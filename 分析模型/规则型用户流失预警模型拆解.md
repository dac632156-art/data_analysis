# 规则型用户流失预警模型 · 三段式算法拆解

> 核心作用：基于"**距上次登录天数**"等硬性时间阈值，对用户打上"**已流失 / 流失预警 / 正常**"三档标签。
> 拆解逻辑（用户定的尺子）：第一段 硬性阻断层 HardBlock（把门）→ 第二段 基座计算层 Base（立核心，最优先）→ 第三段 进阶探测层 Advanced（从 Base 的流失/预警上深入探究）。
> 下游目的：本拆解即后端（Python / Pandas）代码规格——据此直接生成 `churn_rule.py` 计算模块（`validate_input` + `compute_base` + `compute_advanced_e/f`）。
> 一句话大白话：拿一把"尺子"（动态流失阈值 = 群体平均购买间隔的两倍，比如大家平均 30 天买一次、那 60 天没动静就判流失）把用户量一遍，自动给每人贴"已流失 / 流失预警 / 正常"三档标签——把快跑路的客户提前筛出来，让运营趁早去挽留，别把昨天刚买的健康客户也塞进预警池。类比小区门禁：谁超过"平时刷卡间隔的两倍"还没刷卡（登录），系统就标红"这人可能搬走了"，保安（运营）好上门问问要不要续费。

## 第一段：硬性阻断层（HardBlock）—— 输入数据校验

- **校验对象**：Pandas DataFrame 列名
- **必备列集**：$C_{core} = \{\text{用户ID},\ \text{订单时间}\}\ \text{且互动/参与度信号集合}\ \mathcal{A} = \{\text{事件时间},\ \text{会话开始时间}\}\ \text{中至少一个存在}$
  - `用户ID`：分组主键（一用户一行，按用户聚合产出流失标签）
  - 互动/参与度信号（来自映射词典原生列，代表"用户来过、有行为"）：`事件时间`(event_time，泛指登录/浏览/点击等行为事件时间戳，最宽泛的活跃信号)、`会话开始时间`(start_time，访问会话起点)。模型取其中**实际存在的列**，于 Base 2.0 按用户取最大值聚合出 `最后活跃时间`（详见 2.0）。**关键区分**：`订单时间`/`支付时间`/`加购时间` 属**交易信号**（衡量"买没买"，本质是购买活跃度、即 `最近购买间隔天数` 轴），**不计入** `最后活跃时间`——混用会把"只加购/只下单但长期不登录"的用户误判为活跃，系统性低估流失；若业务显式定义"购买即活跃"，可配置 `include_purchase_as_activity=True` 将交易信号并入，默认关闭。`最后活跃时间`本身不再进白名单——它是派生特征（=互动信号最近一次时间的最大值），由模块内部算出，遵循白名单只列原生列铁律。
  - `订单时间`：虽属交易信号（衡量"买没买"，归购买活跃度轴）、**不计入 `最后活跃时间`**，但作为 R_churn（2.1.5 群体平均购买间隔 × 2）计算的必选输入，已列入 $C_{core}$——无则整体 `skipped`，不会进入 Base。
- **阻断**：若 $\text{用户ID} \notin \text{原始列}$ 或 $\text{订单时间} \notin \text{原始列}$ 或 $\mathcal{A} \cap \text{原始列} = \varnothing$（即无任互动信号、仅有交易信号且未开启 `include_purchase_as_activity`）→ `return {"status":"skipped"}`（跳过非报错）
- **标注**：`MD 算法阻断`
- **取列**：仅做列名存在性校验，不取数；要求原始表含 `用户ID` + `订单时间` 且至少一个互动信号列方可进入 Base。

> 白话：规则型流失预警的"门槛原料"就两类——**谁**要被判定（用户ID）、**这人最近一次"来过/有行为"是哪天**（互动信号：事件时间或会话开始时间）。`最后活跃时间`不是传进来的，是模型拿这些原生互动时间列按用户取最大值自己算出来的；下单/付款/加购是"买"的事，不算"活跃"，别混进来。`距上次登录天数`同理，由 Base 内部从 `最后活跃时间` 算出（保证口径统一，不受上游衍生列命名/精度差异影响）。

## 第二段：基座计算层（Base Calculation）—— 模型最核心分析

**目标**：原始活动明细（含 `用户ID` + `订单时间` + 至少一个互动信号列）→ 经 2.0 按用户聚合出用户级表 $[\text{用户ID},\ \text{最后活跃时间}]$ → 每用户一行 `距上次活跃天数` $R_{login}$ + **三档流失状态**标签（$\{\text{已流失},\ \text{流失预警},\ \text{正常}\}$）+ 群体统计。这是规则型流失预警的灵魂，必须先立稳。

### 2.0 最后活跃时间计算（派生聚合 · 仅互动信号）· MD

- **取列**：取 $\{\text{用户ID}\}$ + 互动信号集合 $\mathcal{A}_{present} = \mathcal{A} \cap \text{原始列}$（$\mathcal{A} = \{\text{事件时间},\ \text{会话开始时间}\}$，来自映射词典原生列；若 `include_purchase_as_activity=True` 才额外并入 $\{\text{订单时间},\ \text{支付时间},\ \text{加购时间}\}$）。
- **公式**：
$$\text{最后活跃时间}(u) = \max_{c \in \mathcal{A}_{present}} \Bigl( \max_{\;o:\ \text{用户ID}(o)=u} \text{time}_c(o) \Bigr)$$
即：仅对**互动/参与度信号**取该用户最近一次时间（用户级 MAX），再跨信号取最大值，得到"最后一次有任何行为"的时间点。**交易信号默认不参与**——它们衡量的是购买而非活跃（见 HardBlock 说明）。若输入已是按用户预聚合、直接带 `最后活跃时间` 列的表，可跳过本步直接消费（便捷路径，非白名单契约路径）。
- **变量说明**：`事件时间`(event_time) 覆盖最宽泛行为（登录/浏览/点击），其存在时 `最后活跃时间` 最贴近真实活跃；`会话开始时间`(start_time) 表示一次访问的开始。两者均属"用户来过"的实证。交易列（订单/支付/加购）默认排除，因它们衡量购买而非活跃——若并入，一个"昨天加了购物车但半年没登录"的用户会被错判为活跃，系统性低估流失。
- **白话**：这人最后一次登录、浏览、点击或访问是哪天，就记哪个——这就是"最后活跃时间"。下单/付款/加购不算"活跃"（那是买的事，归购买活跃度轴管）。
- **数据形状（Data Shape）**：用户级宽表 $[\text{用户ID},\ \text{最后活跃时间}]$（每用户一行，连续时间戳）→ 作为 2.1 的输入。

### 2.1 距上次活跃天数计算 · MD 数学公式

- **取列**：取 $\{\text{用户ID},\ \text{最后活跃时间}\}$（最后活跃时间由 2.0 产出）+ 分析基准日 $T_{ref}$。
- **公式**：
$$R_{login}(u) = T_{ref} - \text{最后活跃时间}_u \quad\text{（距上次活跃天数）}$$
- **变量说明**：$T_{ref}$ = **数据快照基准日**，默认取数据集所代表时间窗口的"当下"（典型实现：取上游订单表 $\max(\text{订单时间})$，或业务显式指定快照日）；**仅当数据是实时流（截至运行当日）时才取当前分析当日**。CLV 模型中已有同口径规范（绝对距离/绝对阈值对基准日敏感，绝不可取"当前真实日期"硬顶历史快照）。
- **白话**：每个用户多久没活跃了——基准日减去最后一次活跃时间，单位天。这是流失判定的唯一基础量。
- **数据形状（Data Shape）**：用户级宽表 $[\text{用户ID},\ R_{login}]$（每用户一行连续值）。

### 2.1.5 流失阈值计算（群体平均购买间隔 × 2，写死）· MD

- **取列**：取 $\{\text{用户ID},\ \text{订单时间}\}$（`订单时间` 来自映射词典【高频核心】，订单级原生列；仅供算阈值，**不计入** `最后活跃时间`）。
- **公式（单用户平均购买间隔）**：对用户 $u$ 的全部订单时间升序排列 $t_{u,1}<t_{u,2}<\dots<t_{u,n_u}$，若 $n_u\ge 2$ 则：
$$\bar{g}_u = \frac{1}{n_u-1}\sum_{k=1}^{n_u-1}(t_{u,k+1}-t_{u,k})$$
（仅 $n_u=1$ 的单次购买用户无法算出间隔，不计入群体均值。）
- **公式（群体平均购买间隔）**：对所有多单用户取均值：
$$\bar{G} = \frac{1}{|U_{multi}|}\sum_{u\in U_{multi}}\bar{g}_u,\quad U_{multi}=\{u:n_u\ge 2\}$$
- **公式（流失阈值，写死）**：
$$R_{churn} = 2 \times \bar{G}$$
- **变量说明**：$R_{churn}$ 为**流失阈值**，写死算法 = 群体平均购买间隔 × 2（电商直觉：一个人超过"平时两次购买间隔的 2 倍"还没动静，即视为流失风险信号）。`订单时间` 属交易信号，仅用于算阈值，不参与 `最后活跃时间`（活跃轴与购买轴分离，见 HardBlock）。无 `订单时间` 时模型在 HardBlock 即 `skipped`（已列入 $C_{core}$ 必选），不会到本步，故无回退路径。
- **白话**：先算所有人"平均隔多久买一次"，再乘 2 当作流失红线——比如大家平均 30 天买一次，那 60 天没动静就判流失。阈值跟着数据走，不再拍脑袋写死 180。
- **数据形状**：标量 $[R_{churn}]$（单值，供 2.2 判定使用）。

### 2.2 三档标签判定（核心输出）· MD 数学公式

- **取列**：取 $[\text{用户ID},\ R_{login}]$ + 流失阈值 $R_{churn}$（由 2.1.5 算出的标量；`订单时间` 已列入 $C_{core}$ 必选，无回退路径）+ 群体平均购买间隔 $\bar{G}$（同由 2.1.5 算出，作预警起点）。
- **公式**：
$$\text{流失状态}(u) = \begin{cases} \text{已流失}, & R_{login}(u) > R_{churn} \\ \text{流失预警}, & \bar{G} < R_{login}(u) \le R_{churn} \\ \text{正常}, & R_{login}(u) \le \bar{G} \end{cases}$$
- **变量说明**：$R_{churn}=2\bar{G}$ 为**流失阈值**（算法详见 2.1.5，依赖 `订单时间` 列，已列入 $C_{core}$ 必选、无回退）；$\bar{G}$ 为群体平均购买间隔（阈值的一半，作预警起点）。**三档定义**：① $R_{login} > R_{churn}$（超平均间隔 2 倍）→"已流失"（明确离场，可清理归档）；② $\bar{G} < R_{login} \le R_{churn}$（超平均间隔但不到红线）→"流失预警"（观察期、需运营主动介入）；③ $R_{login} \le \bar{G}$（尚在平均购买节奏内）→"正常"（健康活跃，不进预警池）。补"正常"档可避免把"昨天刚买"的活跃客户误塞进预警池、浪费触达成本。
- **白话**：距上次活跃超过阈值（平均间隔×2，如 60 天）→ 已流失（可清理归档）；介于平均间隔与阈值之间（如 30~60 天）→ 流失预警（需运营触达）；还在平均购买节奏内（如隔 1 天）→ 正常（健康，不浪费触达）。三档分清水路，预警池只装真在观察期的人。
- **数据形状**：宽表新增 $[\text{流失状态}]$（每用户一行离散标签 $\in \{\text{已流失},\ \text{流失预警},\ \text{正常}\}$）。

### 2.3 群体统计 · MD 数学公式

- **取列**：取 2.2 输出 $[\text{流失状态}]$。
- **公式**：
$$N_{churned} = \bigl|\{u \mid \text{流失状态}(u) = \text{已流失}\}\bigr|$$
$$N_{warned} = \bigl|\{u \mid \text{流失状态}(u) = \text{流失预警}\}\bigr|$$
$$N_{normal} = \bigl|\{u \mid \text{流失状态}(u) = \text{正常}\}\bigr|$$
$$\text{流失率} = \frac{N_{churned}}{N_{churned} + N_{warned}} = \frac{N_{churned}}{N}$$
$$\text{健康率} = \frac{N_{normal}}{N}$$
- **白话**：把每类标签的人数清点出来——已流失多少人、预警多少人、正常（健康）多少人、整体流失率多少（与 CLV 的 $\hat{c}$ 同口径，CLV 内部仍自算）；健康率反映"仍在正常购买节奏内"的占比，供运营区分"该救的"与"好好养的"。
- **数据形状**：标量 $[N_{churned},\ N_{warned},\ N_{normal},\ \text{流失率},\ \text{健康率}]$。

### 2.4 基座可视化产出（计算层 → 决策层桥梁）

- **群分层对比图（三档）**：对比 `已流失` / `流失预警` / `正常` 三档人数。业务作用：一眼看"沉睡池规模"vs"预警池规模"vs"健康池规模"，定运营资源分配（预警池是触达目标、沉睡池是挽回目标、健康池是维护目标）。
- **距上次活跃天数分布直方图**：数据来源 2.1 的 $R_{login}$ 列。业务作用：看分布形态——是双峰（有明显预警/已流失断层）还是连续（阈值设得是否合理）。若分布连续且 $R_{churn}$ 附近密度高，提示阈值需调整。
- **流失标签导出表**：每用户一行 `用户ID` + `流失状态` + $R_{login}$，可直接对接运营系统的"沉睡用户召回名单 / 高风险用户预警名单"。

**基座输出**：用户级宽表 $[\text{用户ID},\ R_{login},\ \text{流失状态}]$ + 群体统计 $[N_{churned},\ N_{warned},\ N_{normal},\ \text{流失率},\ \text{健康率}]$。

## 第三段：进阶探测层（Advanced Probe）—— 从 Base 的流失/预警上深入探究

触发（入口契约）：进阶分支**输入锚定 Base 输出的 `流失状态`**（已流失 / 流失预警 / 正常），**只做对"已流失"+"流失预警"两群人的下钻 / 归因 / 分群 / 排序，最多加附加标记列，绝不回改 `流失状态` 主标签**。每个分支独立判断——仅当自身**探测列**存在于输入、且 Base（2.1 ∧ 2.2）跑通时才调用对应 `compute_advanced_*`，多支可并存。入口判断 = 探测列存在性校验 + Base 成功校验（详见各支「入口 / 触发判断」）。基座不变，进阶只在其上做下钻深挖。

### E 流失/预警群价值分层（探测列：CLV / 总消费金额 / 可现场计算的订单金额）· MD+1

- **价值来源（三选一，优先级从高到低）**：
  1. `CLV`：上游 CLV 模型输出的客户生命周期价值列（本模块只消费，不重算）；
  2. `总消费金额`（累计消费额）：映射词典键 `总消费金额`（变体含"累计消费/用户GMV/用户终身价值/ltv"），数据中已直接存在则直接消费；
  3. **现场计算**：当上述两列均不存在，但 `用户ID`（已在 $C_{core}$ 必选）与订单金额列（`订单实付金额` / `订单总额` / `购买金额` 任一）存在时，按用户 SUM 现场算出累计消费额：
     $$\text{累计消费额}(u) = \sum_{o:\ \text{用户ID}(o)=u} \text{订单金额}(o)$$
     其中 `订单金额` 取 `订单实付金额` / `订单总额` / `购买金额` 中实际存在的那一列（优先级同序）。
- **入口 / 触发判断**：E 对 Base 已判出的**"已流失"与"流失预警"两群人**按价值切高/中/低，输出 `挽回优先级` 标记。故依赖 **2.2 跑通**（已有 `流失状态` 列）；**且**价值来源至少一个可得。代码入口：`compute_advanced_e(df, base_result)` 在 **2.2 返回运行成功后**按下式判定 trigger 非空才调用：
  `trigger = [c for c in ["CLV","总消费金额"] if c in df.columns]`；若为空，则校验 `("用户ID" in df.columns) and any(col in df.columns for col in ["订单实付金额","订单总额","购买金额"])` —— 满足即走现场计算路径，trigger 视作非空；两者皆不满足则 E `skipped`。
- **算法推导**：设用户价值 $V(u)$ = 上述任一来源得到的价值（CLV 优先；其次 `总消费金额`；再次现场算出的累计消费额）；按全体价值分布分位切三档（阈值可配 `value_q` 默认 `[0.7, 0.3]`，即前 30% 高价值、后 30% 低价值）：
$$V_{tier}(u) = \begin{cases} \text{高价值}, & V(u) \ge Q_{0.7} \\ \text{中价值}, & Q_{0.3} < V(u) < Q_{0.7} \\ \text{低价值}, & V(u) \le Q_{0.3} \end{cases}$$
$$\text{挽回优先级}(u) = \begin{cases} \text{紧急挽回}, & \text{流失状态}(u)=\text{已流失} \ \text{AND}\ V_{tier}(u)=\text{高价值} \\ \text{重点防护}, & \text{流失状态}(u)=\text{流失预警} \ \text{AND}\ V_{tier}(u)=\text{高价值} \\ \text{标准召回}, & \text{流失状态}(u)=\text{已流失} \ \text{AND}\ V_{tier}(u)=\text{中价值} \\ \text{常规跟进}, & \text{流失状态}(u)=\text{流失预警} \ \text{AND}\ V_{tier}(u)=\text{中价值} \\ \text{停止触达}, & \text{流失状态}(u)=\text{已流失} \ \text{AND}\ V_{tier}(u)=\text{低价值} \\ \text{常规维持}, & \text{流失状态}(u)=\text{流失预警} \ \text{AND}\ V_{tier}(u)=\text{低价值} \\ \text{（不标记）}, & \text{流失状态}(u)=\text{正常} \end{cases}$$
- **数学公式变更**：不改动 `流失状态` 主标签；仅新增 `价值层` + `挽回优先级` 两附加列。价值层 × 流失状态全展开为 6 个互斥动作标签（每格动作不重叠、可操作），消除旧版"高/中价值不分状态、仅低价值分状态"的双标。
- **输出数据**：宽表新增 $[\text{价值层}]$（高/中/低）+ $[\text{挽回优先级}]$（紧急挽回/重点防护/标准召回/常规跟进/停止触达/常规维持/不标记）→ 直接回答"判出流失然后呢"：高价值已流失紧急挽回、高价值预警重点防护、中价值已流失标准召回、中价值预警常规跟进、低价值已流失停止触达、低价值预警常规维持，资源按格精准投放。

### F 流失归因 / 特征对比（探测列：上游维度列集合，至少一个存在才跑）· MD+1

- **探测列（完整清单，来自映射词典实际字段，按域分组；标「分箱」=连续数值需先切区间再对比；本模块不重算，直接消费上游已存在的维度列）**：
  - **用户属性域**：性别、年龄（分箱）、教育水平、收入（分箱）、婚姻情况、城市、省份、国家、会员等级、用户状态、客户年限（分箱）、忠诚度计划、订阅状态、设备类型、平台、流量来源、广告来源、营销计划
  - **商品域**：商品类目、类目ID、品牌、商品规格
  - **订单/交易域**：订单状态、支付方式、优惠券（是否用券）、退款状态、承运商、订单送达率（分箱）、客诉次数（分箱）、折扣比例（分箱）
  - **评价域**：评分星级、客户满意度
  - **模型标签域（上游衍生，可直接当维度）**：用户分层、价值等级、流失风险等级、客户细分、聚类标签、新客标记、复购标记、购买状态
  - **实验域**：AB分组
  （说明：天然离散字段如性别/城市/会员等级/商品类目/订单状态/支付方式直接分组对比；连续数值如年龄/收入/客户年限/订单送达率/客诉次数/折扣比例，F 跑时需先按分位或业务区间分箱成离散区间再对比偏移。）
- **入口 / 触发判断**：F 对比"**流失群**（已流失）vs **正常群**"在各维度上的分布差，找出流失集中点。故依赖 **2.2 跑通**（已有 `流失状态`）；**且**上列维度中至少一个存在。代码入口：`compute_advanced_f(df, base_result)` 在 **2.2 返回运行成功后、且 `trigger = [c for c in 维度列完整清单 if c in df.columns]` 非空** 才调用；trigger 为空则 F `skipped`，不报错。有几个维度算几个，每个维度独立算偏移、独立产出排名。
- **算法推导**：对每个维度 $d \in \mathcal{D}_{present}$，计算流失群在该维度各取值上的占比偏移（与正常群基线比）：
$$\text{偏移}_d(k) = P(\text{维度}=k \mid \text{流失状态}=\text{已流失}) - P(\text{维度}=k \mid \text{流失状态}=\text{正常})$$
偏移越大，说明该维度取值 $k$ 上流失越集中（如某品类偏移 +0.4 = 流失用户里该品类占比比正常用户高 40pct）。
- **数学公式变更**：不改动 `流失状态` 主标签；产出各维度的"流失集中度排名"。
- **输出数据**：宽表新增 $[\text{流失集中维度TOP}]$ 标记（每用户一行，标注其最显著的流失集中维度取值）→ 暴露"流失集中在哪类业务场景"（某品类/渠道流失高 = 对应选品或渠道质量问题），给运营"为什么会流失"的归因抓手。

### 进阶可视化产出（叠加在 Base 之上）

- **E 价值分层 → `bubble_matrix__retention_priority`（ECharts bubble 图 · 气泡矩阵 / 挽回优先级矩阵图）**：`series.type="scatter"`、`symbolSize` ∝ 人数；xAxis=价值层（ordinal: 高/中/低）、yAxis=流失状态（ordinal: 已流失/预警，**该轴数据直接取自 Base 2.2 算出的 `流失状态` 列，E 不重算**）。后端 `echart_generator` 产出字典 key = `bubble_matrix__retention_priority`，前端 `EChartView` 按此 key 取 option。业务作用：一眼锁定各格名单——高价值已流失=紧急挽回、高价值预警=重点防护、中价值已流失=标准召回、中价值预警=常规跟进、低价值已流失=停止触达、低价值预警=常规维持。

## 与现有模块的衔接（不重复造轮子）

- **本模块与 CLV 共享 $T_{ref}$ 口径**：两模型均依赖"数据快照基准日"，需在传数契约层统一（典型做法：从上游订单流 $\max(\text{订单时间})$ 取一次、各模块共用）。本模块的 `流失状态` 标签可作为 CLV 算 $\hat{c}$ 时的输入（CLV 内部仍按自身口径自算，不直接读取本标签——遵循白名单铁律）。
- **本模块与"购买活跃度"信号的关系**：上游"最近购买间隔天数"衍生指标衡量购买节奏，本模块的 $R_{login}$ 衡量登录/行为节奏。两者信号不同（行为 vs 下单），本模块独立计算，不依赖任何上游分层模型；输出可作为交叉验证参考（用户登录沉默但下单活跃 = 上游购买健康、本模块预警——典型分歧场景）。
- **本模块与用户画像互补**：本模块产出"是否流失"的**单维标签**；用户画像模型产出"按群分层的画像"——本模块标签可作为用户画像的**输入分群键**（把"流失状态"三档作为切片维度，看正常群 / 流失预警群 / 已流失群的画像差异，正常群作健康基准对照）。
- **无降级兜底关系**：本模块不触发其他模块；HardBlock 不齐就 `skipped`，独立自包含。
- **白名单铁律一致**：本模块 $C_{core} = \{\text{用户ID},\ \text{订单时间}\}\ \text{且互动信号}\ \mathcal{A}=\{\text{事件时间},\text{会话开始时间}\}\ \text{中至少一个}$（`订单时间` 为交易信号、不计入"最后活跃时间"，但作为 R_churn 计算必选列已列入 C_core；`支付时间`/`加购时间` 默认不计入活跃轴，归购买活跃度（即 `最近购买间隔天数`）轴）只列原生列；`最后活跃时间` 现由 Base 2.0 内部算出（=互动信号列的用户级 MAX），不进白名单；距上次登录天数 / 流失状态 / 价值层 / 挽回优先级 等均**不进白名单**，由 Base/Advanced 内部算出。HardBlock 校验逻辑可与其他模型（如 CLV）复用 `validate_input` 框架（仅替换 $C_{core}$ 集合）。

## 交叉校验结论

$C_{core}$（`用户ID` + `订单时间` 必选，且互动信号集合 $\mathcal{A}=\{\text{事件时间},\text{会话开始时间}\}$ 中至少一个；`订单时间` 为交易信号、不计入"最后活跃时间"但作为 R_churn 计算必选列已列入 C_core，`支付时间`/`加购时间` 默认不计入活跃轴，归购买活跃度（即 `最近购买间隔天数`）轴）均已存在于 `映射词典.md`：

- `用户ID` → 词典【高频核心】；
- `事件时间` → 词典【高频核心】（行为与流量，互动信号）；`会话开始时间` → 词典【进阶可选】（行为与流量，互动信号）；
- `订单时间` → 词典【高频核心】（交易与订单）、`支付时间` → 词典【进阶可选】（支付、折扣与退款）、`加购时间` → 词典【进阶可选】（购物车与关联推荐）——三者均属**交易信号**，默认不计入本模型 C_core，仅当 `include_purchase_as_activity=True` 才并入；
- `注销时间` / `账号封禁状态` → 词典原生列区（【进阶可选】）；
- `最近购买间隔天数` / `在站时长` → 词典"模型分析指标"区（【进阶可选】，上游衍生指标计算模块产出）；
- `注册日期` → 词典原生列区（【高频核心】）。

**无需扩充词典**。

> 注：`最后活跃时间` 不再进 C_core 白名单——它现由本模块在 Base 2.0 从原生**互动信号列**（$\mathcal{A}$，即`事件时间`/`会话开始时间`）按用户取最大值**内部算出**（=各互动信号最近一次行为时间的最大值），属派生特征；交易时间列不参与（避免购买轴冒充活跃轴）。词典中"距上次登录天数"同理属【进阶可选】衍生特征（=$T_{ref}$-`最后活跃时间`），不进白名单。本模块一律从原生时间列重算，不读取任何外部传入的衍生列，保证口径统一。
