# 分析模型算法拆解：动态自适应转化漏斗模型（AARRR/AIPL 兼容版）

---

## 目标模型：行为路径转化漏斗模型

将离散的用户行为事件日志，通过动态模型嗅探、严格的时间序列校验与身份去重，转化为标准序列降维矩阵，据此计算业务节点流失率，为全栈重构提供后端 Python/Pandas 代码规格。

---

## 第一段：硬性阻断层（HardBlock）—— 数据校验与嗅探预处理

**校验对象**：传入的 Pandas DataFrame 行为事件宽表。

**必备列集**：

```
C_core = {"用户ID", "行为类型", "事件时间"}
```

### 1.1 基础缺失阻断（MD 算法阻断）

**推导逻辑**：如果输入数据缺少上述三个必备列，直接抛出跳过指令，终止计算。

```python
if not {"用户ID", "行为类型", "事件时间"}.issubset(df.columns):
    return {"status": "skipped"}
```

**大白话讲解**：没"用户ID"算不了人头，没"行为类型"分不清动作，没"事件时间"排不了先后。这三样缺一不可，缺了直接退回，防止后端报错崩溃。

### 1.2 动态模型嗅探与路由匹配（MD+1 预处理阶段）

**推导逻辑**：提取表中所有的去重行为类型，预设两套或多套模型配置，进行降级匹配。

```
Config_AARRR = ["访问", "加购", "活跃", "支付", "分享"]
Config_AIPL   = ["曝光", "加购", "支付", "复购"]
```

**匹配规则**：如果数据包含 AARRR 的所有事件，则 Steps = Config_AARRR；若不包含，则嗅探 AIPL；若均不包含，则提取出现频次最高的 `top_n_events`（默认 5，可配置）个事件生成自定义漏斗。

**大白话讲解**：在正式算账前，先摸一次底。看看用户传上来的数据够不够拼成 AARRR，不够的话就降级去拼 AIPL。这叫"看菜下饭"，一套代码适应不同客户的数据厚度。

### 1.3 脏数据清洗与排序（MD+2 预处理阶段）

**推导逻辑**：过滤掉不在匹配 Steps 中的冗余事件，标准化时间格式，并按用户、时间进行强排序：

```python
df.sort_values(by=["用户ID", "事件时间"])
```

**大白话讲解**：把漏斗不关心的杂七杂八的操作全扔掉给内存减负，然后把每个人的行为按时间从早到晚排好队，梳理成一本"行为流水账"。

---

## 第二段：基座计算层（Base Calculation）—— 模型最核心分析

**计算目标**：将整理好的有序流水账，转换为 `(i=漏斗步骤, j=留存人数/流失率)` 的一维序列矩阵。

### 2.1 首层基数提取（Define Base Audience）

**推导逻辑**（MD）：从排序后的宽表中，提取完成 Step₁ 的独立"用户ID"，并求其最早的"事件时间"（即 T₁）。

**数学公式**：

$$U_1 = \{\, u \mid \exists\, t(u,1),\ \text{Action}\bigl(u, t(u,1)\bigr) = \text{Step}_1 \,\}$$

$$T(u,1) = \min\{\, t \mid \text{Action}(u,t) = \text{Step}_1 \,\} \quad\text{（用户 } u \text{ 最早到达 Step}_1 \text{ 的时刻）}$$

**数据形状**：生成临时 DataFrame 映射表 `[用户ID, T₁]`。

**大白话讲解**：把第一关（起点）的通关名单拉出来，并记下每个人第一次进门的时间。这批人就是算整个漏斗转化率的"绝对分母"。

### 2.2 递进时间约束匹配（Sequential Join）

**推导逻辑**（MD+1）：针对 Step₂ 乃至 Stepₙ，将上一层的临时表与原始表做 Left Join，严格要求"用户ID"一致，且当前动作时间 ≥ 上一动作的时间。

**数学公式**：

$$U_i = \{\, u \in U_{i-1} \mid \exists\, t(u,i) \ge T(u,i-1),\ \text{Action}\bigl(u, t(u,i)\bigr) = \text{Step}_i \,\}$$

$$T(u,i) = \min\{\, t \mid t \ge T(u,i-1) \land \text{Action}(u,t) = \text{Step}_i \,\} \quad\text{（用户 } u \text{ 在上一步之后最早到达 Step}_i \text{ 的时刻）}$$

**数据形状**：原表通过递进 Merge，延展为包含各层级到达时间的宽表 `[用户ID, T₁, T₂, ..., Tₙ]`。

**大白话讲解**：拿着上一关的存活名单去对下一关的账。系统严格审查：必须是同一个人，且完成下一关的操作必须在上一关之后。任何时间逻辑倒错的作弊者（比如先买单后加购）都被无情筛掉。

### 2.3 计数聚合与转化率输出（Aggregation）

**推导逻辑**（MD+2）：针对宽表中的 T₁ 至 Tₙ 列，执行非空去重计数。计算相邻层级的商得单步转化率，除以 U₁ 得总转化率。

**数学公式**：

$$\text{Count}_i = |U_i| \quad\text{（第 } i \text{ 步的存活用户数）}$$

$$\text{CR}_{\text{step}}(i) = \frac{|U_i|}{|U_{i-1}|} \quad\text{（第 } i \text{ 步人数 ÷ 第 } i-1 \text{ 步人数）}$$

$$\text{CR}_{\text{overall}}(i) = \frac{|U_i|}{|U_1|} \quad\text{（第 } i \text{ 步人数 ÷ 第 1 步人数，分母始终是起点总人数）}$$

**数据形状**：输出标准的漏斗一维数组结果 `[Step_Name, Count, Step_CR, Overall_CR, Funnel_Type]`（附带识别出的模型标签）。

**大白话讲解**：每过一关清点一遍还剩几个活人，算菜单步留存和总体留存，最后盖上一个戳（比如"当前渲染模型：AIPL"），发给前端画图。

## 第三段：进阶探测层（Advanced Probe）—— 从核心往深里挖

基于核心的序列逻辑，传入指定列时触发，深入探测漏斗细节。

### 分支 A：多维切片漏斗（流量质量探究与阻断）

**探测列**：`{"流量来源"}` 或 `{"平台"}`。

**算法推导变更**（MD+1）：在提取基数时带出维度变量 `d`。执行维度分组聚合计算 `CR_overall(n, d)`。引入业务配置红线：最低渠道转化率红线（`Alert_CR_Low`），输出动作指令以叫停劣质渠道的投放。

**数学公式变更**：

$$\text{CR}_{\text{overall}}(n, d) = \frac{|U(n,d)|}{|U(1,d)|} \quad\text{（渠道 } d \text{ 端到端总体转化率，告警判定取末步 } n\text{）}$$

基于红线生成系统下发动作：

```
                        ┌ '渠道质量预警(Channel_ROI_Warning)',   若 CR_overall(n, d) < Alert_CR_Low
System_Action(d)   =    ┤
                        └ '优质渠道(Healthy_Channel)',           其他情况
```

**阈值确定（Alert_CR_Low）**：默认动态 = `0.6 × median({CR_overall(n,d) | d ∈ 所有渠道})`（渠道转化率低于同行中位数 60% 即判劣质），经验系数 0.6。暴露覆盖入口：配置项 `alert_cr_low`（绝对数）存在时优先使用该绝对数。渠道数 < 2 时中位数退化无意义，回退为 `alert_cr_low` 绝对数；若亦缺失则用整体漏斗 CR × 0.5 兜底。

**输出数据**：按渠道拆分的多组漏斗数组，并追加对应渠道的动作指令标签 `System_Action`。

**可视化产出**：`hbar__channel_conversion`（ECharts 横向 `bar`）。y 轴 = 渠道类目，x 轴 = 该渠道总体转化率 $\text{CR}_{\text{overall}}(n,d)$，按 `System_Action` 着色（渠道质量预警=红 / 优质渠道=绿）。图的作用：把各渠道转化质量排排坐，标红即踩及格线，市场部一眼看出"哪些渠道在浪费投放预算"，直接做加减预算决策。此 key 为后端 `echart_generator` 产出字典 key，前端 `EChartView` 按 key 取 option（项目 option 契约）。

**大白话讲解 / 解决盲区**：原来是个大漏斗，现在按渠道劈成小漏斗。算出转化率后，后端拿去跟设定的及格线比对。如果发现某家广告代理商拉来的流量（比如抖音渠道）走到最后一步的转化率连底线都没达到，系统直接输出"渠道质量预警"指令，通知市场部立刻停止对该渠道的预算投入。

### 分支 B：极速转化窗口阻断（转化节奏探究）

**探测列**：`{"会话ID"}`（事件时间已含于 C_core 恒可用；B 以会话ID存在为触发条件，公式强依赖会话相等约束）。

**算法推导变更**（MD+2）：在基座 2.2 时序匹配中，追加绝对隔离条件：Step_i 的"会话ID"必须等于 Step₁ 的"会话ID"。引入系统配置参数：最大会话有效窗口（`Max_Session_Window`，如 30 分钟），作为会话中断的兜底时间校验。

**数学公式变更**（B 以 base 的 $U_1$ 为种子构建**自有严格集** $U^{\text{fast}}_i$，逐级在自身上一严格步 $U^{\text{fast}}_{i-1}$ 上叠加会话相等+窗口约束，**不引用 base 的 $U_{i-1}$**，否则被前步筛掉的用户会在后步被 base 集重新算入、严格漏斗失效）：

$$U^{\text{fast}}_i = \{\, u \in U^{\text{fast}}_{i-1} \mid t(u,i) \ge T^{\text{fast}}(u,i-1) \land \text{SID}(u,i) = \text{SID}(u,1) \land \bigl(t(u,i) - T^{\text{fast}}(u,1)\bigr) \le \text{Max\_Session\_Window} \,\}$$

（其中 $U^{\text{fast}}_1 = U_1$，$T^{\text{fast}}(u,k)$ 为严格链中用户 $u$ 到达第 $k$ 步的最早时间）

**输出数据**：更为严苛的单次有效会话存活矩阵 `U^{fast}_1..U^{fast}_n`（B 自有严格漏斗，作为 Base 标准漏斗的**补充**；标准漏斗取 Base 层 2.3 输出、极速漏斗取本分支 `U^{fast}`，两 funnel 数据需一并传给前端绘制对比图）。

**可视化产出**：`funnel__session_vs_full`（ECharts `funnel`，双 series 并排：标准漏斗 vs 极速漏斗）。两漏斗各步存活/转化率对齐，重点看两图之间的"缺口"。图的作用：把"页面当场转化力"显形——若极速漏斗在中后步大幅塌缩，说明用户不是被页面刺激当场下单，而是逛完走人、靠后续回想才转化（UX 收割力缺失）。此 key 为后端 `echart_generator` 产出字典 key，前端 `EChartView` 按 key 取 option。

**大白话讲解 / 解决盲区**：不仅要求动作都在一次打开 App 的记录里，还要加上"30 分钟"的时间锁。剔除掉那些把 App 挂在后台挂了一下午才买的异常订单，系统只考核这批人在 30 分钟内有没有被页面刺激到"立刻冲动消费"。

### 分支 C：终点 GMV 挂载（商业变现探究与拦截）

**探测列**：`{"订单实付金额"}`。

**算法推导变更**（MD+2）：在漏斗抵达最后一步 Stepₙ 时，计算存活用户的客单价 `AOV`。引入业务配置红线：客单价极值红线（`Alert_AOV_Low`），如果该漏斗跑进来的全是低价值羊毛党，输出预警。

**数学公式变更**：

$$\text{GMV}_n = \sum_{u \in U_n} \text{订单实付金额}(u) \quad\text{（所有到达最后一关的用户掏的钱全部加起来）}$$

$$\text{AOV}_n = \frac{\text{GMV}_n}{|U_n|} \quad\text{（总金额 ÷ 到达终点的人数）}$$

基于红线生成系统下发动作：

```
                          ┌ '低净值流量预警(Low_Quality_Traffic_Alert)',   若 AOV_n < Alert_AOV_Low
System_Action     =       ┤
                          └ '高价值转化(High_Value_Funnel)',               其他情况
```

**阈值确定（Alert_AOV_Low）**：C 仅产出单一漏斗 `AOV_n`、无渠道维度可互比，故阈值不可"数据内相对"。默认动态基线 = `0.7 × AOV_baseline`，`AOV_baseline` 必须为**模型外注入的业务历史整体客单价**（配置项 `aov_baseline`，由订单表全量独立计算或业务直接填）。**严禁从本漏斗输入内的订单实付金额推算 baseline**——否则 baseline 必等于 `AOV_n` 自身，`0.7×baseline` 恒 ≥ `AOV_n`，低净值预警永不触发。经验系数 0.7。暴露覆盖入口：配置项 `alert_aov_low`（绝对数）存在时优先。若 `aov_baseline` 与 `alert_aov_low` 均未提供，退化为绝对经验默认 `Alert_AOV_Low_default = 50`（单位：元，经验占位值，业务须按品类认领/覆盖，否则可能误报或漏报）。

**输出数据**：在漏斗尾部节点追加输出 `Total_GMV`、`Avg_Order_Value` 以及动作指令标签 `System_Action`。

**可视化产出**：`bar__aov_by_funnel`（ECharts `bar`）。x 轴 = 漏斗类目（C 仅按单漏斗产出，无渠道维度），y 轴 = 平均客单价 $\text{AOV}_n$，按 `System_Action` 着色（低净值流量预警=红 / 高价值转化=绿）。图的作用：暴露"高转化低客单价"的羊毛党陷阱——当该漏斗客单价柱标红（低于基线），说明这批转化对利润毫无价值，防止"转化率高但全是一两元低价单"的虚假繁荣。此 key 为后端 `echart_generator` 产出字典 key，前端 `EChartView` 按 key 取 option。

**大白话讲解 / 解决盲区**：漏斗不仅要数走到最后付款的人头，还要算客单价。防止遇到"转化率极高，但全是花一毛钱买包邮抽纸"的业务陷阱。一旦系统发现最终客单价低于设定的红线，哪怕转化率是 100%，系统也会立刻拉响"低净值流量预警"，说明这批流量对提升公司利润毫无价值。

## 附录：符号速查表

| 符号 | 含义 |
|------|------|
| u | 某个用户 |
| Uᵢ | 到达第 i 步的存活用户集合 |
| Step_i / Step₁ | 漏斗第 i 步 / 第 1 步（起点）的行为类型 |
| T(u,i) | 用户 u 到达第 i 步的最早时间 |
| Action(u, t) | 用户 u 在时刻 t 发生的行为 |
| \|Uᵢ\| | 集合 Uᵢ 的大小，即第 i 步的存活人数 |
| Count_i | 第 i 步的存活用户数（= \|Uᵢ\|） |
| CR_step(i) | 第 i 步的单步转化率 = \|Uᵢ\| / \|U(i-1)\| |
| CR_overall(i) | 第 i 步的总体转化率 = \|Uᵢ\| / \|U₁\| |
| Σ | 求和 |
| SID(u,i) | 用户 u 做第 i 步时的会话 ID |
| Max_Session_Window | 最大会话有效窗口（如 30 分钟） |
| d | 某个流量来源 / 渠道维度 |
| CR_overall(n, d) | 渠道 d 的端到端总体转化率（取末步 n） |
| Alert_CR_Low | 最低渠道转化率红线。默认动态=0.6×全渠道CR中位数；配置 alert_cr_low(绝对)优先；渠道<2 回退整体CR×0.5 |
| System_Action(d) | 渠道 d 的动作指令：渠道质量预警(Channel_ROI_Warning) / 优质渠道(Healthy_Channel) |
| GMV_n | 到达最后一步用户的成交总额 |
| AOV_n | 到达最后一步用户的平均客单价 |
| Alert_AOV_Low | 客单价极值红线。默认=0.7×AOV_baseline(配置,业务历史整体客单价)；配置 alert_aov_low(绝对)优先；均无则退化经验默认 50 元(占位须认领) |
| System_Action | 漏斗动作指令：低净值流量预警(Low_Quality_Traffic_Alert) / 高价值转化(High_Value_Funnel) |
