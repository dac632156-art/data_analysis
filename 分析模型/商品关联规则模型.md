# 分析模型算法拆解：商品关联规则模型（FP-Growth / 购物篮分析）

---

## 目标模型：商品关联规则模型（Market Basket Analysis）

将海量零散的订单明细数据，通过频繁项集挖掘与条件概率计算，转化为标准的商品关联规则矩阵。基于"Support、Confidence、Lift"三大核心指标，发现"买了A的用户大概率会买B"的连带销售规律，为前端商品推荐、套餐打包、页面排版提供后端算法基础。

---

## 第一段：硬性阻断层（HardBlock）—— 数据校验与预处理

**校验对象**：传入的 Pandas DataFrame 订单明细宽表。

**必备列集**：

```
C_core = {"订单ID", "商品ID"}
```

### 1.1 基础缺失阻断（MD 算法阻断）

**推导逻辑**：如果输入数据缺少上述两个必备列，直接抛出跳过指令，终止计算。

```python
def validate(df):
    C_core = {"订单ID", "商品ID"}
    if not C_core.issubset(df.columns):
        return {"status": "skipped"}
```

**大白话讲解**：算购物篮，最核心的就是要知道"哪个篮子（订单ID）"里装了"哪些货（商品ID）"。缺了篮子编号，不知道哪些商品是一起买的；缺了商品编号，篮子就是空的。只要缺一个，模型直接罢工。

### 1.2 脏数据清洗与极值截断（MD 预处理阶段）

**推导逻辑**：剔除单笔订单中只包含 ≤ `min_basket_size` 件商品的记录（默认 `min_basket_size = 1`，即仅含 1 件的订单，无法产生关联）；剔除单笔订单包含异常多商品（> `max_basket_size` 件，默认 `max_basket_size = 500`，可能是 B 端批发刷单，会严重污染 C 端推荐规则）的记录。**两阈值均为可配置参数**，调用方按业务调整；默认值写死，保证不传配置也能跑。

**大白话讲解**：只买了一根葱的单子直接扔掉，因为没产生任何"搭配"。批发商进货一次买 500 样东西的单子也扔掉，这叫离群值，把这种数据放进池子会把正常的规律带偏。

**⚠️ 分母口径与偏差注意**：
- 下游 2.2 的总篮子数 $N$ 必须是**经本步清洗后的**篮子数（剔除单件 / 异常多件后的计数），全程统一使用 `N_clean`，不得用原始订单数。
- 剔除单件订单会系统性剔除"只买 X、没搭配"的负样本，使 `Confidence(X→Y)` 偏向"在多件订单中、买了 X 也买 Y 的条件比例"，而非无条件的 `P(买Y | 买X)`。若业务要求 Confidence 把单件-X 订单计为负样本，应保留单件订单（仅剔除异常多件）。本模型默认剔除单件，故下游 Confidence 语义为"多件篮内的条件置信度"，须在接口文档中明示。

## 第二段：基座计算层（Base Calculation）—— 模型最核心分析

**核心大白话讲解**：这层只算最硬核的数学概率。把所有订单当成一个总池子，找出哪些商品组合经常一起出现，并算出"买了 A 的篮子也更可能含 B"的同篮共现概率（注意：购物篮分析基于同一订单内的共现，无时间先后），以及这俩组合到底是不是真的有互相促进的化学反应。

**计算目标**：将订单明细表转化为 `[前置项X, 后置项Y, Support, Confidence, Lift]` 的关联规则矩阵。

### 2.1 交易篮子重塑（Basket Construction）

**推导逻辑**（MD）：以"订单ID"为维度进行 groupby，将同一订单下的"商品ID"聚合为集合（Set）。

**数学公式**：设所有订单的集合为 T，单个订单为 t(k)，项集为 I。

```
t(k) = { i | 商品 i 属于订单 k }
```

相当于：一个篮子 = 该订单里所有不重复的商品。

**数据形状**：产出二维嵌套数组或列表映射表：`[订单ID, [商品A, 商品B, 商品C...]]`。

**大白话讲解**：把原来一条条按商品列出来的明细账，重新按"人手一个的超市购物篮"打包归类。算出一共有多少个篮子。

### 2.2 频繁项集挖掘与支持度计算（Support Calculation）

**推导逻辑**（MD+1）：遍历所有篮子（或使用 FP-Tree 算法），统计单项集 X（如商品A）和组合项集 X∪Y（如商品A+商品B）同时出现的篮子数量。除以总篮子数 N，得到支持度（Support）。过滤掉低于最小支持度阈值的边缘组合。

**数学公式**：

总订单数 $N = N_{clean} = |T_{clean}|$ = 经 1.2 清洗后的篮子总数（务必使用清洗后计数，详见 1.2 口径注意）

```
Support(X) = 同时包含 X 的篮子数 / N

Support(X∪Y) = 同时包含 X 和 Y 的篮子数 / N
```

写作：

```
Support(X) = 出现 X 的篮子的个数 ÷ 所有篮子个数
Support(X∪Y) = 同时出现 X 和 Y 的篮子的个数 ÷ 所有篮子个数
```

**数据形状**：产出包含高频组合及其 Support 的映射表：`[项集, 出现频次, Support]`。

**大白话讲解**："支持度"就是看这个组合在所有人里火不火。如果 1 万个篮子里只有 2 个篮子同时装了榴莲和牙膏，说明这是极小概率的偶然事件，直接淘汰，不浪费算力。

### 2.3 关联规则生成与核心指标评价（Confidence & Lift）

**推导逻辑**（MD+2）：基于高频组合，计算单向推导规则 X → Y 的置信度（Confidence）与提升度（Lift）。

**数学公式**：

Confidence（买了 X 的人里，有多少也买了 Y）：

```
Confidence(X→Y) = Support(X∪Y) / Support(X)
                 = (同时买了 X 和 Y 的篮子数) ÷ (买了 X 的篮子数)
```

通俗：买了 X 的用户里有百分之几也买了 Y。

Lift（X 对 Y 的真实促进作用，剔除 Y 本身热度的干扰）：

```
Lift(X→Y) = Confidence(X→Y) / Support(Y)
          = Confidence(X→Y) ÷ (Y 在全部篮子中出现的比例)
```

通俗：X 到底把 Y 的销量带飞了多少。

**数据形状**：最终输出核心矩阵 `[前置商品X, 后置商品Y, Support, Confidence, Lift]`。

**大白话讲解**：Confidence 表示买了啤酒的人里有百分之几买了尿布。Lift 最关键：
- Lift = 1：买啤酒和买尿布纯属巧合，各买各的，没有互相影响。
- Lift > 1（比如 1.5）：啤酒把尿布的销量硬生生带飞了 50%，这就是我们要找的"黄金搭档"。
- Lift < 1：买了啤酒反而更少买尿布，可能是互相替代的竞品关系。

## 第三段：进阶探测层（Advanced Probe）—— 从核心往深里挖

基于核心的关联规则，当传入字典数据中包含指定的【进阶可选】列时触发，深入探测搭售细节。

### 入口契约总纲（触发判定与并存执行顺序）

**触发判定（基于传入字典的探测列是否 presence）**：

| 分支 | 触发条件（传入字典须含以下列） | 作用域 |
|------|-------------------------------|--------|
| A 跨类目 | `商品类目` | 改写篮子物品粒度（SKU→类目） |
| B 利润挂载 | `商品毛利`（或 `商品单价` / `折扣金额`） | 在基座结果上追加财务列 |
| C 人群切分 | `用户分层`（按 `用户ID` 关联的客群映射）**且**底层订单明细须含 `用户ID` 列 | 进基座前按人群切分数据 |

**正交性与并存**：A / B / C 三者作用域互不重叠——A 改"篮子里的物品是什么粒度"，B 改"结果挂什么财务列"，C 改"拿哪些行进计算"。三者**可任意并存叠加**，不存在互斥。

**并存执行顺序契约**（多分支同时触发时固定按此顺序，保证结果可复现）：

```
1. C 前置：仅当同时具备「传入 `用户分层` 映射」且「订单明细含 `用户ID` 列」时，按 用户ID→用户分层 将订单明细按客群物理切分；二者缺一则 C 不触发，整体为单子集。
2. A 改写：若传 `商品类目`，在每个子集内将篮子物品由 商品ID 替换为 商品类目。
3. 基座计算：对每个子集按第二段 2.1→2.2→2.3 算出规则矩阵。
4. B 挂载：若传 `商品毛利`，在每条规则上按 C1 口径计算并追加 Avg_Margin / Total_Revenue。
```

### 分支 A：跨类目搭售探测（品类规划深挖）

**探测列**：`{"商品类目"}`。

**算法推导变更**（MD+1）：在 2.1 重塑篮子前，将"商品ID"映射替换为"商品类目"。基座挖掘的对象从"具体 SKU 组合"提升维度为"类目组合"。

**数学公式变更**：项集空间由 SKU 维度替换为类目维度。

```
t(k) = { c | 商品类目 c 属于订单 k }
```

相当于：一个篮子 = 该订单涉及的所有不重复类目。

**输出数据**：类目级别的关联矩阵（如：母婴品类 → 家居家纺品类）。

**大白话讲解 / 解决盲区**：基座算的是"大蒜和排骨"的关联。但有时候具体商品变动太快，这个进阶直接拔高一层，算"生鲜区和调料区"的关联。这能直接指导线下超市怎么摆货架，或者线上商城的大类目导航怎么排版。

### 分支 B：连带利润真实度挂载（虚假繁荣剔除）

**探测列**：`{"商品毛利"}`（或 `{"商品单价"}`, `{"折扣金额"}`）。

**算法推导变更**（MD+2）：在算出 X → Y 规则后，关联财务字段，计算所有同时包含 X∪Y 的订单的平均毛利额。

**数学公式变更（聚合口径严格定义）**：

设订单 $o$ 的明细行集合为 $L_o$，第 $l$ 行的商品数量为 $q_l$、毛利为 $m_l$（若无独立毛利列，则以 `商品单价 − 折扣金额` 近似；缺失数量列时默认 $q_l=1$）。

- 当 A 未触发（X / Y 为 SKU）：
  $$
  \text{MarginOrder}(o, X\cup Y) = \sum_{l\in L_o,\; \text{商品ID}_l \in \{X,Y\}} m_l \cdot q_l
  $$
- 当 A 已触发（X / Y 为类目）：
  $$
  \text{MarginOrder}(o, X\cup Y) = \sum_{l\in L_o,\; \text{商品类目}_l \in \{X,Y\}} m_l \cdot q_l
  $$

$$
\text{Avg\_Margin}(X\cup Y) = \frac{\sum_{o:\; o\text{ 同时含 }X\cup Y} \text{MarginOrder}(o, X\cup Y)}{|\{o:\; o\text{ 同时含 }X\cup Y\}|}
$$

即：把"同时买了 X 和 Y 的订单"里、属于 X / Y 的那几行毛利（按数量加权）全部加总，再除以这些订单的条数，得到每单平均毛利。

**输出数据**：在核心矩阵尾部追加 `Total_Revenue`（上述分子）与 `Avg_Margin`（上述商）字段。

**大白话讲解 / 解决盲区**：有些商品虽然天天被一起买（比如买鼠标送一块钱的鼠标垫），Lift 很高，但根本不赚钱甚至倒贴。这个进阶直接用利润透视关联规则，找出那些既有关联性，又能真实拉动客单价和毛利的"现金牛套餐"。

### 分支 C：高价值人群专属特质探测（人群异质性与动作下发）

**探测列**：`{"用户分层"}`。

**算法推导变更**（MD+1）：在执行 2.1 之前，基于传入的"用户分层"，将原始数据集物理切割。对不同客群并行计算基座模型，并挂载特定的营销下发指令。

**数学公式变更**：

第一步，定义客群子集 T_segment，计算各客群内的 Support：

```
Support_segment(X) = 该客群的篮子中同时包含 X 的篮子数 / 该客群的篮子总数
```

即：同样算 Support，但只在某个特定人群的篮子里算。

第二步，基于客群差异生成系统下发动作（动作映射可配置，不写死两档）：

```
# action_map：键 = 用户分层列中实际出现的分段取值，值 = 下发动作标签
# 本模型与分层来源完全无关——分段可由业务标签、人工规则或任意上游字典产生，模型只把该列当透明分类变量
action_map = {
    "高价值段": "VIP_Targeted_Bundle",
    "次高价值段": "VIP_Targeted_Bundle",
    "一般段": "Standard_Bundle",
    "低价值段": "Standard_Bundle",
    # ... 键须与实际分段取值一一对齐，由调用方按自身分层体系填写
}
# 默认规则：命中 action_map 高价值键 → VIP_Targeted_Bundle；其余（含未命中） → Standard_Bundle
System_Action(segment) = action_map.get(segment, "Standard_Bundle")
```

即：具体"哪些分段算高价值"由调用方通过 `action_map` 配置，键必须与传入 `用户分层` 列的真实取值对齐（无论该分层来自何种上游体系：业务标签、人工规则或任意上游字典均可）；不再写死"VIP / 普通"两档，未命中键的统一回落 `Standard_Bundle`。

**输出数据**：不同客群特有的搭售矩阵，并输出具体动作指令标签（如 `Action: VIP_Targeted_Bundle`）。

**大白话讲解 / 解决盲区**：穷人和富人的购物车装的东西绝对不一样。进阶算出不同人群的差异化规则后，直接输出营销指令。

比如系统发现高价值 VIP 买了冲锋衣后极大概率会买登山杖，接口直接输出指令标签 `VIP_Targeted_Bundle`，触发前端页面专属推荐；而羊毛党则不会收到该推荐位。

## 数据注入与编排约定（进阶列的外部来源）

本模型严格独立：基座与各进阶分支**只消费传入的列，不生产、不调用、不依赖任何上游模型**。进阶触发列（`商品类目`、`商品毛利`、`用户分层`、`用户ID`）均不由本模型计算，而是由**编排层（后端 Pipeline）在调用本模型前注入**到输入 DataFrame。

### 列从哪来（以 C 分支的 `用户分层` 为例）

C 分支所需的 `用户分层` 列，本模型自身算不出、原始订单里也没有，其来源只能是外部：

- **外部分段模型产出**：如 RFM 用户分层、K-means 用户聚类等业务上游，各自独立跑完会下车一个 `(用户ID → 分层标签)` 的产出物；
- **编排层注入**：后端把上述产出物按 `用户ID` join 进 订单明细，使输入 DataFrame 多出 `用户分层` 列后，再调用本模型；
- **本模型零耦合**：模型代码内从不 `import` 或调用 RFM / K-means，它只读取已存在的 `用户分层` 列。分段具体由谁生成、取值叫什么，模型不关心（`action_map` 键对齐实际取值即可）。

> 这与「用户画像模型」已定的 **双源拼接（原始标准列 ⊕ RFM/K-means 输出）** 是同一套编排机制——上游产出作为可选注入列进入下一模型，模型之间保持函数级解耦。

### 两级门槛：启动 vs 跳过

| 门槛 | 判定条件 | 后果 |
|------|----------|------|
| 模型级（HardBlock） | 缺 `订单ID` / `商品ID` | 整个模型 `skipped` |
| 分支级（L3 入口） | 进阶列缺失（如 C 缺 `用户分层` 或订单行无 `用户ID`） | **仅该分支跳过**，其余照常跑 |

要点：**基座不依赖任何进阶分支**。即使完全不注入 `用户分层`（即不跑 RFM / K-means 也能）本模型仍可纯跑原始订单得到 base +（若有）A/B 结果；C 的"启动"只取决于"注入列在不在"，与上游模型是否运行无代码关联。

### 后端"公交车"流示意

```
[RFM 站]    读订单/客户 → 下车 {用户ID: 分层}  ──┐
                                                 ├─→ [编排器] 按 用户ID join
[K-means站] 读特征      → 下车 {用户ID: 簇ID} ──┘     进 订单明细 → 多一列 用户分层
                                                 │
[商品关联规则站] 输入 = 订单明细(订单ID,商品ID,用户ID[,用户分层])
                → 有 用户分层? → C 点火 ; 无 → C 跳过、base 照跑
```

每站模型独立，数据表像公交车流经；模型间零函数耦合，仅通过"编排层注入列"传递信息。

## 附录：符号速查表

| 符号 | 含义 |
|------|------|
| T | 所有订单（篮子）的集合 |
| t(k) | 第 k 个订单（篮子） |
| N = \|T\| | 总篮子数 |
| X, Y | 单项集或组合项集（一个或一组商品） |
| X∪Y | 项集 X 和 Y 的并集（两个商品同时出现） |
| X → Y | 关联规则：买了 X 会买 Y |
| Support(X) | 多少比例的篮子包含 X |
| Confidence(X→Y) | 买了 X 的篮子里，也买了 Y 的比例 |
| Lift(X→Y) | X 对 Y 的真实带动倍数（>1 才有效） |
| Avg_Margin(X∪Y) | 同时包含 X 和 Y 的订单的平均毛利额 |
| Support_segment(X) | 某客群子集中包含 X 的篮子比例 |
| T_segment | 某个人群子集的篮子集合 |
| System_Action(segment) | 该客群的下发动作标签，由可配置 `action_map` 映射（默认：高价值段→VIP_Targeted_Bundle，其余→Standard_Bundle） |
