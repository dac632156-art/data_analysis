## 用户需求

上线版本的上传功能必须提示「最大 50MB」，且当用户尝试上传大于 50MB 的文件时，上传应当失败并显示警告。

## 产品概述

DataMind AI 数据分析工具的文件上传入口（宇宙传送门组件）。当前线上版本存在两处不一致：前端 UI 文案提示 50MB，但前端 dropzone 并未真正拦截 >50MB 文件；后端真实上限为 200MB（本地 .env 覆盖为 5GB），与「提示 50MB」不符。

## 核心修复目标

- 后端线上真实上限改为 50MB（无 .env 环境生效），超限返回 413 警告
- 前端真正拦截 >50MB 文件（useDropzone 增加 maxSize），超限时显示深空风格红色警告且不发请求
- 保持前端「最大 50MB」提示文案不变，本地开发（.env=5GB）不受影响

## 技术栈

- 前端：React + TypeScript + Vite + Tailwind CSS（原子类）
- 后端：FastAPI（Python）
- 改动文件：`config.py`、`frontend/src/components/FileUploader.tsx`（仅两处）

## 实现方案

### 方法

通过调整后端默认上限为 50MB，并在前端 dropzone 真正插入 `maxSize` 拦截 + `onDropRejected` 警告回调，使前后端在「50MB」上一致且超限即失败报警。

### 关键技术决策与理由

1. **后端 `config.py` 默认值 200→50**：线上部署无 `.env`（被 gitignore），走 `config.py` 默认值。改为 `int(os.environ.get("MAX_UPLOAD_SIZE_MB", 50))` 后，线上真实上限即 50MB。`MAX_FILE_SIZE_BYTES` 与 `upload.py` 的 413 文案（`f"文件大小超过 {MAX_UPLOAD_SIZE_MB}MB 限制"`）自动联动为 50MB，无需改 upload.py。本地 `.env=5120` 仍覆盖为 5GB，开发不受影响，零回归。
2. **前端 `FileUploader.tsx` 补 `maxSize` + `onDropRejected`**：当前 `useDropzone` 缺 `maxSize`，且无 `onDropRejected`，导致 >50MB 文件被照常 `onUpload` 发往后端、无任何前端警告。新增 `maxSize: MAX_SIZE_MB * 1024 * 1024` 实现真正前端拦截；`onDropRejected` 中检测 `file-too-large` 错误并 `setError`；`onDrop` 开头 `setError(null)` 清空，避免历史警告残留。
3. **警告渲染复用深空暗色体系**：在 L88-98 提示区下方条件渲染 `<p className="text-xs text-rose-400">{error}</p>`，使用 danger 色 `#FB7185`/rose 系，贴合既有银河紫暗色风格，不引入新依赖、不改 Props 契约、不改视觉层级。

### 性能与可靠性

纯客户端校验（dropzone 在选文件阶段即拦截，不发网络请求），无额外渲染开销；后端 413 为既有轻量校验路径。无状态/重渲染副作用。

### 实现注意（防止回归）

- 仅改 `config.py` 默认值与注释、FileUploader 的 dropzone 配置与警告渲染，绝不改动上传流程、会话管理、解析信号量逻辑。
- 注释需同步更新：说明线上默认 50MB、本地 `.env` 可覆盖到 5GB、GitHub HEAD 默认即 50MB（原「永不更改!200MB」注释作废）。
- **部署提醒（非代码改动但必须告知）**：线上当前显示 5GB 说明其运行版本 ≠ 当前 git HEAD。本计划改完后必须重新构建并重新部署前后端，线上才会真正变为「提示 50MB + 拦截 50MB」，否则仍是老版 5GB。

## 架构设计

不涉及架构变更。后端 `upload.py` 继续依赖 `config` 的 `MAX_FILE_SIZE_BYTES`/`MAX_UPLOAD_SIZE_MB`；前端 `FileUploader` 维持 `{ onUpload, disabled }` Props 契约，仅内部新增 `error` 本地 state。
