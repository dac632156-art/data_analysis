# 内存画像与 512MB 实例容量分析

> 目的：量化「数据看板后端部署在 Render 免费实例（512 MB RAM）能否扛住真实流量」，把「512MB 够不够」从猜测变成数据。
> 日期：2026-07-13
> 适用对象：后端 FastAPI + uvicorn + numpy + pandas + LLM SDK；部署目标 Render 免费版（512 MB / 0.1 CPU，ephemeral disk ≈ 386 GB）。

---

## 一、为什么做这份内存画像

1. **部署约束**：项目部署在 Render 免费实例，硬上限 **512 MB RAM** + 免费版 15 分钟无流量即休眠、ephemeral 文件系统每次 deploy 清空。
2. **点 1 决策悬而未决**：此前新增「原始数据落盘（`/tmp/datamind_original/*.pkl`）以省内存」的逻辑，本质是「用磁盘换内存」。其是否成立，取决于实例临时盘配额与内存是否共享——但 Render 免费版**不提供 Shell/SSH**，无法直接 `df -h /tmp` 查配额。
3. **直觉误区需要纠正**：团队对「内存到底花在哪」只有模糊印象（以为大头是数据常驻、报告线程），需要用实测拆解「空转基线 / 数据膨胀 / 双拷贝 / 会话常驻 / 报告线程 / 上传尖峰」各自的占比。
4. **避免 OOM 上线事故**：512MB 实例一旦并发上传大文件或并发生成报告，可能因瞬时 RSS 飙升被 OOM killer 杀进程。上线前必须先知道「真正的内存杀手是谁」。

> 临时查配额的方式：在 `main.py` 临时加 `/api/debug/disk` 端点（无 Shell 时唯一查配额路径），部署后浏览器访问拿到 `disk_total_mb=395700`（≈386 GB）、`disk_free_mb=64030.5`（≈62.5 GB），确认临时盘与内存独立且极度宽裕，随后已删除该端点。

---

## 二、内存画像（6 点规格 · 实测）

### ① 空闲基线（最关键，最易被忽略）
- 空闲基线 RSS ≈ **112.3 MB**（FastAPI + uvicorn + numpy + pandas + 全 `src.*` 路由 + LLM SDK 全加载后、未接任何请求）。
- ⚠️ 误区纠正：`openai` 是模块级 import（`agent.py`），且 `report` router 被 `main.py` 常驻 include → 后端一启动就加载 LLM SDK，**基线已含 LLM SDK（不是 lazy）**。
- 结论：512MB 里光「空转」就吃掉 ~112MB，**真实可用约 350MB**。

### ② 单文件膨胀系数（CSV vs XLSX，含解析尖峰）

| 格式 | 磁盘目标 | df 内存 | 磁盘→内存 | 解析 RSS 尖峰 | 尖峰/稳定 |
|------|----------|---------|-----------|---------------|-----------|
| CSV | 1 MB | 1.09 | ×1.1 | +1.3 MB | 1.2× |
| CSV | 5 MB | 5.45 | ×1.1 | +2.7 MB | 0.5× |
| CSV | 20 MB | 21.8 | ×1.1 | +9.3 MB | 0.4× |
| CSV | 50 MB | 54.5 | ×1.1 | +18.6 MB | 0.3× |
| XLSX | 1 MB | 1.68 | ×1.7 | −0.1 MB | — |
| XLSX | 5 MB | 8.39 | ×1.7 | +33.1 MB | 3.9× |
| XLSX | 20 MB* | 9.42 | ×1.7 | +32.8 MB | 3.5× |
| XLSX | 50 MB* | 9.42 | ×1.7 | −31.5 MB | — |

\* XLSX 因 openpyxl 读取太慢，cap 到 10 万行（实测 5.5MB 磁盘），膨胀倍数与尖峰趋势不变。

- **CSV**：稳定 ×1.1，磁盘≈内存，几乎不「虚」。
- **XLSX 磁盘「虚」**：同样内存的数据，xlsx 磁盘只有 CSV 的 ~60%（×1.7）——看到 5MB 的 xlsx，实际数据有 8.4MB。
- 🔴 **最危险的是 XLSX 解析尖峰**：openpyxl 解压+建对象时，瞬时 RSS 飙到 df 内存的 **3.5–3.9 倍**（5MB xlsx 尖峰 +33MB）。一个 20MB xlsx 上传瞬间 +33MB，并发上传多个 xlsx 尖峰叠加极易 OOM。

### ③ 双拷贝代价（确认现状）
- 单份 df（30 万行）内存 ≈ 27.1 MB。
- 理论双拷贝（旧逻辑 `df_original=copy + df=copy`）应额外占一份 ≈ 27MB（100%）。实测 RSS 增量 8MB 偏低（内存分配器/GC 复用导致的测量噪声），但性质明确：**点 1 把原始数据落盘后，每会话原始副本 100% 移出内存**。✅ 点 1 决策正确。

### ④ 会话长驻特性
- `session_timeout = 3600s`（1 小时）。
- ⚠️ 无独立后台清理线程 → 清理是**惰性的**（下次请求触发 `_cleanup_sync` / 淘汰最老会话）。会话实际占用可能远超 1 小时，直到下一个请求到来。
- 验证：`set_data` 后 1s 内 df 仍在内存（True，不主动释放）。
- 结论：单用户占用持续且惰性释放；**多人并发叠加才致命**。

### ⑤ 单报告线程占用（stub LLM 实测）
- 串行单任务 RSS 增量 = 0.09 MB；并发 N=5/10 峰值增量 ≈ 0 MB。
- 修正原假设：报告生成的重量在 **LLM 网络 I/O（不占进程 RSS）** 和**会话 DataFrame**，不在「报告线程本身」。
- 结论：**信号量不应按内存设，而应按 LLM 并发速率 / 后端线程数设**。

### ⑥ 阈值公式（画像的输出）
```
M   = 512 MB（实例预算）
B   = 112 MB（空闲基线，含 LLM SDK）
SYS = 50 MB（系统预留）
U0  = M − B − SYS = 350 MB   ← 用户数据可用池

约束 A（会话常驻）：每在线用户 U 占 S（点1后仅工作集）
   S_csv ≈ 磁盘 × 1.1；  S_xlsx ≈ 磁盘 × 1.7
约束 B（上传尖峰）：xlsx 解析瞬时 ×3.9，需单独预算
   建议并发上传数 ≤ floor(U0 / (S_xlsx × 3.9))
约束 C（报告线程）：R ≈ 0.1 MB，可忽略 → 信号量不按内存
```
代入示例（典型 20MB CSV 用户）：单用户常驻 ≈ 21.8 MB；350MB 池约可容 16 个纯 CSV 用户。若含 xlsx：单用户常驻 ~9.4MB 但上传尖峰 +33MB，并发上传建议 ≤ 10 且错峰。

## 三、内存画像的结论

1. **512MB 是账面，真实数据预算池只有 ~350MB**：空转基线 112MB（含常驻 LLM SDK）+ 系统预留 50MB，规划必须按 350MB 而非 512MB。
2. **点 1（落盘原始数据）决策正确，且 Render 上无反噬**：每会话省一份原始副本（100% 移出内存）；Render ephemeral disk 实测 386GB、不共享内存 → 不会触发「落盘失败→兜底塞内存」。
3. **最大 OOM 风险是 XLSX 上传解析尖峰（×3.9），不是数据常驻**：CSV 稳如狗，XLSX 磁盘「虚」且解析瞬间 RSS 飙 3.5–3.9 倍，多并发上传尖峰叠加即瞬爆。
4. **报告线程几乎不占内存（<0.1MB）**：信号量应按 LLM 速率设，不是按内存；当前无限制 daemon 线程的隐患是线程数堆积（阻塞在 LLM I/O），不是内存堆积。
5. **会话清理是惰性的，实际占用可能远超 1 小时**：无后台线程 → 过期会话等下次请求才删；多人并发 + 惰性清理是致命组合。
6. **量化容量**：20MB CSV 单用户 21.8MB → ~16 纯 CSV 并发；xlsx 上传尖峰 +33MB → 并发上传 ≤10 且错峰。

## 四、反映了什么问题

1. **「512MB 实例」是误导性指标**：真实可用池被基线 + 系统预留吃掉 1/3，按账面规划必然高估容量。
2. **团队对内存分布存在直觉误区**：误以为大头是「数据常驻 / 报告线程」，实测证明二者都不是——真正杀手是 **XLSX 解析瞬时尖峰**和**惰性会话堆积**。若不画像，优化会打错方向（例如去限流报告线程，却放任 xlsx 并发上传爆内存）。
3. **点 1 的「用磁盘换内存」在 Render 上成立，但依赖「临时盘不共享内存」这一前提**：若部署到 tmpfs 共享内存的平台（如部分容器/Serverless），点 1 收益归零甚至变负。该结论**平台相关**，换部署目标须重新画像。
4. **架构存在两处限流缺失**：① 上传接口对 XLSX 解析尖峰无并发上限；② 报告接口用无限制 `threading.Thread(daemon)`，高并发提交会无脑堆线程（虽不堆内存，但堆连接/堆 LLM 请求）。
5. **会话生命周期管理薄弱**：只有惰性清理，无后台定时回收，长尾会话会占用内存远超 timeout 设定。

---

## 五、落地建议（优先级）

| 优先级 | 项 | 说明 |
|--------|----|------|
| **P0** | XLSX 上传尖峰并发上限 / 流式读 | 最大 OOM 风险点，多并发大 xlsx 会瞬爆 512MB |
| **P1** | 报告 `asyncio.Semaphore(3~5)` | 按 LLM 速率限流，防线程/连接堆积（内存不是瓶颈） |
| **P2** | 后台定时清理线程 | 补惰性清理短板，避免会话卡死超 1 小时不释放 |
| — | 点 1 落盘 | 已正确，无需改动 |

> 注：本报告数据基于 Render 免费实例实测。换部署平台（尤其 tmpfs 共享内存的 Serverless）须重新执行画像，结论可能反转。
