# 列名映射子系统

把上传数据表里的「千奇百怪的原始列名」（user_id / uid / 金额数据 / 客户编号…）在**开始分析**时统一重命名为少数**规范标准名**（用户ID / 成交金额 / 性别…），让下游图表生成、多表外键合并使用一致的语义列名。

> 核心动机：客户表和订单表都有 `name`，含义不同，写进映射词典不知归入哪个 —— 这是**同名列跨表歧义**问题，靠「表级指纹」而非单列词典解决。

## 两层结构

| 层 | 文件 | 作用 | 存什么 |
|---|---|---|---|
| 全局无歧义词典 | `src/mapping/column_mapping_dict.yaml` | 用户维护 | `标准字段: [变体...]`（变体→标准字段 一一对应，无歧义） |
| 表级指纹库 | `src/mapping/mapping.db`（SQLite） | 自动生成 | `指纹 → {原始列: 标准字段}` 完整映射 |

## 匹配流水线（按优先级，全部只在「当前仍未映射列」上补充，绝不覆盖词典已映射结果）

1. **词典精确匹配**：列名直接命中词典变体 → 标准字段。
2. **词典相似匹配（≥70%，仅中文列名）**：仅当列名含中文时，才与词典变体做相似匹配——变体⊂列名（如 `金额`⊂`金额数据`）视为 1.0 直接命中；否则 `difflib.SequenceMatcher.ratio() ≥ 0.7` 才命中。**英文/数字列名跳过本步，只走第 1 步精确匹配**，避免短英文（如 `usr_id` / `Dt_Customer`）被字符级算法误命中。
3. **指纹精确匹配**：`fp = sha256(sorted(归一化列))`（忽略列序）→ 命中历史表，仅补充未映射列。
4. **包含度 ≥80%**：`|新表列 ∩ 历史列| / |新表列|`。
5. **相似度 >70%**（Jaccard）：`|交| / |并|`。
6. **多候选裁决**：取最高分；并列时比对各候选对「未映射列」的映射子集是否一致，一致则用、不一致交 LLM。
7. **LLM 对齐兜底**：只把仍未映射列交 LLM，prompt 带【现有标准字段清单】，**先复用已有标准字段、不新造**；都无合适才自定义（中文语义、避免同义重复如「成交金额」vs「成交额」）。缺 api_key/调用失败 → 退化为已有映射，不阻断分析。
8. **落库**：`fp → 完整映射` 写入 SQLite，供同结构表秒级复用。

> 有歧义的列（如 `name`）已故意不写进词典，只能靠第 3~7 步按整表列组合解析归属。

## 相似度算法原理（第 2 步）：字符级，不是分词级

`difflib.SequenceMatcher` 是在**字符序列**上比较，**不是**按词 / token 分词比较。两个字符串的相似度 `ratio = 2 × M / (len(a) + len(b))`：

- `M` = 两边匹配上的**字符总数**（算法递归找最长公共子串并累加，比「第 i 位 == 第 i 位」的朴素逐位比较更优，但**粒度仍是字符**）；
- `len(a) + len(b)` = 两个字符串长度之和。

代码入口 `similarity_match()`（第 108–116 行）先判**子串包含**（一方是另一方子串 → 直接 1.0），否则才用 `SequenceMatcher.ratio()`。

### 实例：`Dt_Customer` 为何被误判成 `用户ID`

- 归一化：`Dt_Customer → dt_customer`（11 字符），词典变体 `customer_id`（11 字符）。
- 两者不是子串包含关系 → 走 `SequenceMatcher`。
- 公共匹配块是 `"tomer_id"`（8 字符），`M = 8`，`T = 11 + 11 = 22`，`ratio = 2×8/22 = 0.7273`。
- `0.7273 ≥ 0.7` 阈值 → **命中** → 被错判为用户ID；又因与 `ID` 已映射的「用户ID」重名，加后缀变成荒谬的「用户ID_2」。
- ⚠️ 注：此前口算为 0.818 是错误的，**真实值 0.7273**（用 `python -c "import difflib; print(difflib.SequenceMatcher(None,'dt_customer','customer_id').ratio())"` 实算）。
- **修复逻辑**：给 `注册日期` 加变体 `dt_customer`，归一化后与 `Dt_Customer` **完全相等**（第 1 步精确匹配 1.0），优先级高于第 2 步的 0.7273，自然抢回正确归属，无需删除合法的 `customer_id` 变体。
- **2026-07-24 新增根因防护**：`Dt_Customer` 是英文列名（不含中文），自本日起第 2 步模糊匹配度搜索**对其直接跳过**（`_is_chinese(col)` 为 False → `continue`）。也就是说 0.7273 这个误判值**根本不再被计算**，从根上杜绝英文短名列蹭阈值的坑；且 `dt_customer` 已作为 `注册日期` 的精确变体，第 1 步即正确命中，无需依赖模糊匹配。中文脏列名（如「金额数据」）仍走第 2 步，行为不变。

> 启示：阈值 0.7 + 字符级算法，意味着「含相同字母片段」的列容易蹭过阈值。抑制误判靠**高优先级精确 / 子串命中**（1.0）去压制低分相似命中，而不是单纯调高阈值（调太高会漏掉真正该映射的脏列名）。

## SQLite 落库：内存与磁盘占用

「落库 SQLite」= 把映射关系持久化进一个**文件型数据库**（`mapping.db`，就是一个文件，不用装 MySQL/PostgreSQL 服务，Python 内置 `sqlite3` 即可）。

- **触发时机**：**上传 ≠ 落库**。上传只把列名记进内存 session；点「开始分析」才打开 `mapping.db` 查/写。
- **内存（RAM）**：几乎为零。SQLite 是文件型，每次只「开连接→查/插一条→关」，内存里仅命中那一条记录（几百字符），不把整库加载进内存。
- **磁盘**：一张表 < 1KB；且 `fingerprint_id` 是**主键去重** —— 同一结构表（同一指纹）只存一条，第二次直接复用、不再插，故体量增长很慢。

## 集成点

- `backend/routers/analysis.py`：`_process_one`（主路径 一键处理）与 `api_analysis_run`（次路径 手动分析）在取清洗后 df、生成意图之前插入 `map_dataset_columns(session_id, dataset_id, df, llm_cfg)`，返回重命名后的 df 再进流水线。
- `dataset_id` 在次路径（`manager.get_data` 取 session 级单表）不存在，故该参数**可选默认 None**，指纹只基于 columns 计算。
- packages 内嵌渲染数据（非回查 session），故只需在进流水线前对 df 重命名即可，无需写回 session。
