# 后端演进史与现状（重构后全貌）

> 从项目开始到现在，后端「实际是怎么搭的、怎么跑的」的大白话全景。重点记录 **2026-07-25 那次大重构**前后的区别——因为知识库里很多旧笔记（含 [[后端技术栈]] 的分层架构）还停留在重构前的目录，本文以「当前磁盘真实状态」为准。
>
> 配套入口：[[后端技术栈]]（MOC）、[[项目架构全景图]]、[[分析流水线现状（点击分析到装包）]]、[[列名映射子系统]]、[[图表渲染架构_后端只出ECharts_option]]。

## 一、一句话结论

后端不是单一 app，而是**两层**：`src/` 是「大脑」（纯 Python 业务核心，不依赖 Web 框架，可被测试直接调），`backend/` 是「嘴巴」（FastAPI 应用层，把 `src/` 的能力通过 HTTP 暴露给前端）。两者通过「分析包（`AnalysisPackage`）」这个结构化对象交接——后端不直接吐 HTML/组件，只产出可被前端消费的数据包。

## 二、整体架构：目录划分与职责

| 层 | 目录 / 文件 | 职责 |
|---|---|---|
| 接入层 | `backend/main.py`、`backend/routers/`、`backend/db/` | app 装配、路由注册、CORS、全局异常、SPA 托管；SQLite 持久化（`db/__init__.py`） |
| 业务核心层 | `src/` 顶层（含 `analysis_engine/`、`mapping/`、`echart_generator.py`、`utils/`） | 分析引擎、列名映射、图表生成、数据清洗校验——全部纯 Python，无 Web 依赖 |

> 与旧架构的区别：旧版还有 `src/planner.py`、`analysis_library/`、`calculators/`、`analysis_templates/`、`stats_analyzer.py`、`reasoning/` 等，已在 2026-07-25 重构中删除（见第七节）。

## 三、请求入口层（FastAPI 路由）

`backend/routers/` 暴露的主要 API（按重构后保留 / 重写口径）：

| Router | 职责 | 状态 |
|---|---|---|
| `analysis.py` | `/analysis/run`、`/analysis/process-datasets`（改调 `run_df_to_packages`） | 保留并重写 |
| `dashboard.py` | `/dashboard/cards`、`/dashboard/kpis`、`/dashboard/echarts` 等；**词云 chart_type 被强制重算**以规避旧包损坏 color | 保留并重写 |
| `report.py` | AI 报告五阶段流水线 | 保留并重写 |
| `chart.py` | ECharts 图表生成 | 保留 |
| `insights.py` | AI 洞察（先保留，Planner 兜底改空列表） | 保留 |
| `stats.py`、`reasoning.py` | 旧描述统计 / 业务推理 | **已删除**（未接线） |

**双层防护（第 2 层）**：5 个高风险路由（`analysis` / `data` / `stats` / `dashboard` / `chart`）返回前都必须经过 `src/utils/json_serializer.py` 的 `sanitize_json` 层——把 NaN / inf / numpy / Timestamp / Decimal 清成 JSON 安全格式，否则前端拿到会崩。详见 [[数据清洗兜底机制]]。

## 四、分析引擎核心：`src/analysis_engine/`（2026-07-25 起唯一分析入口）

这是那次大重构的产物，确定性驱动，不靠 LLM 猜：

| 子模块 | 职责 |
|---|---|
| `base/` | `AnalysisModel` 抽象基类——所有分析模型的契约 |
| `registry.py` | 模型注册表；新模型用 `register_model` 填入 |
| `engine.py` | `run_analysis(df, intents)` 自动跑命中模型，归一化成 `AnalysisPackage` |
| `package_render` | 把包渲染成前端能用的结构 |

**驱动逻辑**：用「映射后列名 ⊆ 模型 required_columns」做确定性匹配。Planner 在候选选择前先对 schema 做**缺失列派生**（确定性规则，非 LLM）：
1. 缺数值指标但有分类维度 → 自动生成 `__derived_count__` 计数指标；
2. 缺日期维度但有 年/月(日) 列 → 合并生成 `__derived_date__`；
3. 缺分类维度 → 放宽选用任意文本列（对词云友好）。
派生成功则不再判 `unsupported`。

> 当前已注册 **8 个模型**（import `models/` 子包即触发模块级注册）：rfm / cohort / clv / kmeans / churn_rule / association_rules / user_profile / funnel。`association_rules_advanced` 由 `association_rules.compute` 内部惰性 import，避免循环依赖。详见 [[分析流水线现状（点击分析到装包）]]。

## 五、列名映射子系统：`src/mapping/` + `mapping.db`

作用：把用户上传的乱列名（金额 / amt / 成交金额）翻译成统一标准字段。8 步流水线（`column_mapper.py`）：
1. 先用 `column_mapping_dict.yaml` 固定词表精确/相似匹配；
2. 算表的「指纹」（列名排序后的 sha256，忽略顺序）；
3. **精确命中** `mapping.db` → 直接复用历史映射；
4–6. **模糊复用**（列重叠度≥0.8 或 Jaccard>0.7）搬历史映射；
7. 都没命中才丢给 LLM；
8. 把本次映射写回 `mapping.db` 供以后复用。

`mapping.db` 是 SQLite 缓存（字段：`fingerprint_id` / `mapping_json` / `columns_json`），有 `_db_lock` 线程锁。**丢了不崩**，只是每次都重走 LLM。它在 git 里标 `modified`，因为每次分析会累积新指纹。详见 [[列名映射子系统]]。

## 六、图表生成：`src/echart_generator.py`

把分析结果变成 ECharts option（前端再渲染，后端不出图）。关键铁律：
- **词云颜色根治**：echarts-wordcloud 2.1.0 的 `textStyle.color=function` 方案彻底无效（全黑无报错）。正解是给每个 data item 直接附静态 `item["textStyle"]={"color": ...}`，series 级只留静态兜底（绝不用 function）。
- 色板 `BLUE_PALETTE` / `WARM_COLORS` 必须和前端 `Palette.ts` **点对点完全一致**（顺序、取值），禁彩虹、禁默认 ECharts 调色板。
- 中国地图 GeoJSON 本地化到 `frontend/public/china.json`，避免阿里云 CDN 跨域失败导致地图空白。详见 [[图表渲染架构_后端只出ECharts_option]]。

## 七、2026-07-25 关键重构（删了什么、留了什么）

**删除**：旧计算/出图层——`planner.py`、`analysis_library/`、`calculators/`、`analysis_templates/`（留 `base.py` 契约）、`stats_analyzer.py`、`reasoning/`、`dashboard_builder.py`、4 个旧 renderer（kpi/table/insight/conclusion）、旧路由 `stats.py` / `reasoning.py`；并移除 `agent.py` 的 V3「AI 对话意图补强」块（`_get_library` / `_inject_matched_intents`）。

**新增**：`src/analysis_engine/`（base / registry / engine / package_render）作为唯一分析入口。

**留下的孤儿代码**（用户拒绝递归删除命令，仍留磁盘、无外部引用、不崩）：`analysis_library/`、`calculators/`、`reasoning/`、`report/` 四个死目录——待用户决定如何清理。

**验证**：`py_compile` 通过；`analysis_engine` 导入成功且已注册 8 个模型；保留路由 import 全 OK。

## 十、面试可讲的两个真问题（后端硬核故事）

> 下面两节是「能拿去面试讲」级别的问题，按 **背景 → 问题 → 我当时怎么想 → 怎么查/定方案 → 踩的坑 → 结果** 写。不是流水账，是决策与权衡。

### 故事 1：把一团乱麻的分析后端，重构成一个「确定性模型注册表」

**背景**
项目早期分析链路是堆出来的：`planner.py` 负责意图识别，`analysis_library/` + `calculators/` + `analysis_templates/` 负责各类计算，`stats_analyzer.py`、`dashboard_builder.py`、4 个旧 renderer 各自出图表和文案，路由层 `analysis` / `dashboard` / `report` / `chart` 各调各的。问题越来越明显：
- 同一类计算逻辑在多处重复；
- 意图匹配靠 LLM 猜，时灵时不灵，无法单测；
- 加一个新分析类型要改好几个文件，边界不清。

**问题（我当时面对的核心矛盾）**
要让「用户丢一张任意列的表进来 → 系统自动选出能跑的分析 → 算出图表+结论」这件事**可控、可测、不抽风**。LLM 意图匹配在这条链路里是隐患：不可复现、贵、且出错时前端只能显示「不支持」。

**我当时怎么想 / 怎么定方案**
我提的方案是：把分析能力抽象成一个个 `AnalysisModel`，每个模型**自己声明**需要哪些标准列（`required_columns`）；引擎用纯确定性的「映射后列名 ⊆ required_columns」做匹配，命中就跑、缺列就静默跳过。好处：
1. **匹配可控可测**——不再依赖 LLM 猜意图，是一条能写单测的确定性规则；
2. **解耦**——「分析类型」和「计算实现」通过注册表模式解耦，新增分析只要写一个子类 + `register_model` 一行，不动引擎；
3. **前端不再有「不支持」**——缺列就跳过，而不是弹错误提示。

**落地结构（真实代码）**
- `base.py`：`AnalysisModel` 抽象基类，类属性 `name / required_columns / optional_columns / upstream_keys`，`can_run(df)` 用 `required_columns ⊆ df.columns` 判定；`compute()` 返回归一化的 `AnalysisPackage`。
- `registry.py`：`register_model` / `get_models`，一个 list 装所有模型。
- `engine.py`：`run_analysis(df, intents)` 两阶段执行——**Phase 1 生产者**（无上游依赖，串行跑，跑完把「每用户分群宽表」挂到 `upstream` 字典）；**Phase 2 消费者**（如用户画像依赖 RFM 分层）拿 `upstream` 跑。单模型异常只 `continue`，不影响其他。
- `models/__init__.py`：import 子包即触发各模型的 `register_model`（模块级副作用注册），目前 8 个模型：rfm / cohort / clv / kmeans / churn_rule / association_rules / user_profile / funnel。

**踩的坑（面试加分点）**
1. **并发隔离契约**：模型是单例，Web 并发请求会共用同一实例。我在 `base.py` 的 docstring 里立了硬规矩——`compute` 不得原地改传入 df、不得用 `self._xxx` 缓存跨方法中间结果，否则并发会「结果串味」。这是真实踩过的坑（rfm 曾有 `self._seg_table` 缓存，被我点名禁止效仿）。
2. **循环依赖**：`association_rules_advanced` 不能在被 import 时直接注册，改成由 `association_rules.compute` 内部惰性 import，避免循环依赖。
3. **重构不破坏已有路由**：旧路由全保留，只是把内部调用换成 `run_analysis`，靠 `sanitize_json` 双层防护兜住返回安全。

**结果**
分析入口收敛成唯一一个 `run_analysis`，新增分析类型从「改五六个文件」变成「写一个类」。匹配从 LLM 抽风变成确定性规则，可单测、可复现。

### 故事 2：用户表列名千奇百怪，怎么做「列名翻译 + 缓存」不每次都烦 LLM

**背景**
用户上传的表列名完全不可控：「金额」「amt」「成交金额」「订单金额(元)」其实都是一回事。分析引擎靠「标准列名」匹配，所以上传的乱列名必须先翻译成标准字段，否则所有模型 `can_run` 都失败。

**问题**
每次都丢 LLM 翻译太贵太慢，而且 LLM 还可能不稳定。需要一个**本地优先、LLM 兜底的渐进式映射系统**。

**我当时怎么想 / 方案**
设计了一条 8 步流水线（`column_mapper.py` 的 `map_dataset_columns`），原则是「**能本地解决绝不用 LLM，LLM 只兜底仍未映射的列**」：
1. **STEP1 精确匹配**：用 YAML 无歧义词典（`金额→成交金额` 这种固定映射）先过一遍；
2. **STEP1.5 相似匹配**：仅对**中文列名**做模糊匹配（阈值 0.7），英文列名跳过——避免短英文（如 `usr_id`）被误命中；
3. **STEP2 指纹**：`fp = sha256(sorted(归一化列))`，**忽略列顺序**，同一张表换列序也能认出来；
4. **STEP3 精确命中 DB**：指纹完全一样 → 直接复用历史映射；
5. **STEP4/5/6 模糊复用**：包含度 ≥ 0.8 或 Jaccard > 0.7 的历史表，把能补的未映射列搬过来；多候选并列时比对映射子集是否一致，不一致才交 LLM；
6. **STEP7 LLM 兜底**：只剩真正没招的列才送 LLM，且 prompt 里强制「优先复用已有标准字段，别新造同义词」；
7. **STEP8 落库**：把「指纹→映射」写进 SQLite（`mapping.db`），下次同结构表直接命中。

**关键设计决策（面试能展开讲）**
- **指纹用「列名集合的哈希」而非表名**：因为同一业务表用户可能存成不同文件名，但列结构一样，按列集合认比按文件名认准。
- **「宁漏勿误」的模糊策略**：`similarity_match` 里特意规定——变体被更长中文词内嵌（如「退款金额」∈「退款金额备注」）返回 0.0 不命中，避免把修饰列误判成原字段；也不再反向包含（「金额」不会被「退款金额」吞掉）。误映射比漏映射后果严重得多（下游全算错）。
- **只补充不覆盖**：所有历史复用都「只补充当前仍未映射列」，绝不覆盖 STEP1 已做好的词典映射。

**踩的坑**
- `mapping.db` 是运行期缓存，每次分析都写，导致 `git status` 老显示 modified——本质可重建，是否进 `.gitignore` 由你定（待决）。
- LLM 兜底要降级：没配 api_key 时不能阻断分析，降级为「保留原列名」，保证链路不崩。

**结果**
日常 90%+ 的表在 STEP1~STEP6 本地就解完了，LLM 只在遇到真生僻列时才出场，成本和时间都压下来；同结构表二次上传零 LLM 调用。
