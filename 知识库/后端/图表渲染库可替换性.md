# 图表渲染库可替换性：能换，但有约束

> 一句话：**架构上能换 ECharts，但 package 里存的是 ECharts 专有格式的 `option`，不是通用描述，所以不存在「只改一行」的无痛换法。** 换哪类库决定改动落在哪一层。

## 一、为什么「能换」——解耦点

后端 `echart_generator.py` 产出 `option` 字典 → `ChartItem.option` → `AnalysisPackage.charts` → 前端 `EChartView` 用 ECharts.js 渲染（见 [[图表渲染架构_后端只出ECharts_option]]）。
后端「算数值」与「渲染」在 **`option` 这个字典边界**解耦——这是可替换的前提。

## 二、关键约束：option 是 ECharts 方言，不是中立格式

`option` 含 ECharts 专有类型名（`series[].type: "line"|"bar"|"pie"`、`xAxis/yAxis`、`tooltip/legend` 结构）。**别的库读不懂它**，不能直接拖进来吃现有 package 的 option。

> 所以「换库」本质是改 **生成端（emit 什么 schema）** + **消费端（谁来读）**，不是只换前端一个组件。

## 三、两条现实路径

### 路径 A：换成另一个「浏览器实时渲染」库（Chart.js / Plotly.js / AntV G2）
- 渲染仍在前端，package 仍存「配置对象」而非图片。
- 代价：新库读不懂 ECharts option → 改 `echart_generator.py` 吐新 schema，或在中间加**格式转换器**；前端 `EChartView` 整体替换。
- 影响面（全读 `option` 字段，格式一变都得动）：
  - `src/dashboard/widget_generator.py`、`src/dashboard/semantic_widget_generator.py`
  - `src/card_generator.py`
  - `frontend/src/utils/exportEChartsDashboard.ts`
- 专有扩展重写：词云（`echarts-wordcloud`）、3D 地图（`map_3d`）是 ECharts 扩展，换库≈重写这两类图。

### 路径 B：换成「生成图片」的库（matplotlib / Plotly 静态 / 服务端 ECharts）
- 「出图」挪到**后端**（图片是二进制，后端产 PNG 字节/URL）。
- 代价：更大重构——`ChartItem` 装图片引用；`echart_generator.py` 改成出图；所有展示面（看板/报告/卡片/导出）从「init 画布」改「`<img>` 显示」。

## 四、常被忽略的点：只为「要一张图」不必换库

若目的只是**导出图片**（嵌报告/发微信），现栈即可——ECharts 原生支持把 option 导出成图片（`getDataURL` / toolbox `saveAsImage`）。很多「想换能出图的库」的需求用现有导出就能满足。

## 五、全量替换（含 wordcloud / echarts-gl 扩展）的 scope

> 用户原问：「把 ECharts 相关的库都替换了，可以吗」——**可以，无架构死路，但 ECharts 扎进 4 层 + 2 个扩展，工作量分布极不均。**

### 四大层（必须全动）
| 层 | 位置 | 换库动作 |
|---|---|---|
| L1 生成端 | `src/echart_generator.py` | 唯一种 ECharts `option` 的源头；改产出格式或加适配器 |
| L2 前端渲染 | `EChartView`（`echarts.init`/`setOption`） | 换新库 init/render 调用 |
| L3 导出 HTML | `frontend/src/utils/exportEChartsDashboard.ts`（~700 行） | **最重**：内嵌 `echarts@5.5.0` CDN + `makeEChartsScript` 直接操纵 option（过滤、pie/wordCloud/radar 提取、`setOption`、`resize`、`registerMap`） |
| L4 后端消费端 | `dashboard/widget_generator.py`、`semantic_widget_generator.py`、`card_generator.py`、`report_builder.py`、`package_reconstructor.py` 等 | 读 `option` 结构（如 `first["option"]`、`chart.get('option')`）；换格式字段访问跟着改（搜 `src/` 含 echarts/option 的文件约 71 个，多数属此类消费端） |

### 两个 ECharts 扩展（非核心库，须单独找替代）
- **词云**：`echarts-wordcloud`（series type `wordCloud`）→ 独立方案 `d3-cloud` / `wordcloud2.js`。
- **3D/地理地图**：`echarts-gl`（`echarts-gl@2.0.9`）+ `echarts.registerMap('china')` → `deck.gl` / `Mapbox` / 高德 JS。**工作量最大**（看板指挥中心中国地图飞线/散点）。
- 另：`BigScreen/*` 大屏模块也用 echarts（独立紫色美学），若在替换范围也要动。

### 最省力策略：双口子转换器
渲染只从 **`EChartView` + `exportEChartsDashboard.ts` 两个口子**进 ECharts → 可在这两个入口写「ECharts option → 新库 schema」转换器，**后端一行不改**（option 继续按 ECharts 格式产，前端翻译）。前提：新库能吃 ECharts 风格 option（Plotly/AntV 近，Chart.js 差异大需更多映射）。
**但词云、3D 地图无「等价通用 option」格式，转换器救不了，必须单独实现。**

### 工作量排序
导出 HTML（最重）> 3D/地理地图 > 词云 > 生成端 ≈ 前端渲染 > 后端消费端字段。

## 六、结论

> 能换，且能把 wordcloud、echarts-gl 一起换掉。建议策略是「**双口子转换器 + 扩展单独实现**」，而非推倒重来改 71 个文件。
