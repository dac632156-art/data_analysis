# 分析引擎提速方案对比（并行 / 预计算 / 缓存 / 换引擎）

> 对应代码：`src/analysis_engine/engine.py`（`run_analysis` 的 Phase 1 串行 `for model in models` 循环，见 [[分析流水线现状（点击分析到装包）]]）。
> 本文是**选型讨论**，不替业务拍板；四种方案可叠加，不是四选一。

## 〇、现状：为什么"模型越多越慢"

`engine.py:40` 的 Phase 1 是一个**串行 for 循环**——模型 A 算完才轮到模型 B，依次排队：

```python
# engine.py:39-70 Phase 1：生产者（无上游依赖）串行跑
for model in models:
    if getattr(model, "upstream_keys", []):
        continue  # 消费者留到 Phase 2
    if not _match_intents(model):
        continue
    if not model.can_run(df):
        continue
    pkg = model.compute(df)   # ← 一个一个算，前一个没完下一个不动
```

- 总耗时 ≈ 各模型耗时**相加**（串行）。
- 模型从 5 个变 20 个 → 时间大致翻 4 倍，线性增长，没商量。
- Phase 2（消费者，如客户画像依赖 RFM 分群）必须等 Phase 1 跑完拿 `upstream`，本身串行、数量少，不是主要矛盾。
- 前端若只传"选中意图"（`intents` 过滤），命中的模型数量被限定，但**仍在串行循环里挨个算**——所以"只跑命中的"不能解决"整体等很久"。

> 数据规模：用户一般 ≤100MB CSV。这个量级下，瓶颈在"模型数量 × 串行"，不在单表大小；大表 pickle 传给子进程的成本（几百 ms~1-2s）可接受。

## 一、四种方案大白话对比

### A. 多模型并行（互不依赖的一起算）

- **干啥**：Phase 1 那些互不依赖的模型（生产者），雇多个"工人"同时算，`concurrent.futures` 线程池 / 进程池。
- **收益**：总耗时 ≈ **最慢那个模型**，而不是所有加起来。例：5 个各 2s → 串行 10s，并行 ≈2s。跟模型数量强相关，是治"整体等很久"最直接的刀。
- **代价 / 风险**：
  - Python 有 **GIL**（全局锁）。模型里若是纯 Python 循环（CPU 密集、不释放 GIL），用**多线程**（threading）根本并行不了，得用**多进程**（multiprocessing）真并行。
  - 多进程之间传 100MB 的 DataFrame 要序列化（pickle）+ 拷贝，有开销；模型太小、数量少时，"开进程的成本"可能盖过收益。
  - pandas 的向量化操作大多释放 GIL → 这种模型用线程池就能真并行，性价比最高；含大量 Python 循环的模型才需要进程池。
  - 报错分散到各进程，调试变难（但引擎已有"单模型失败不影响其他"的 try/except，冲击可控）。
- **适合**：模型多、单个计算偏"向量化 pandas"、首次分析也想要快。

### B. 共享预计算（公共步骤只算一遍）

- **干啥**：引擎在模型跑之前，先统一算一遍"大家都用得上的底料"（比如统一按用户分组求和、时间列解析），各模型直接取用，别各算各的重复扫全表。
- **收益**：纯减少重复劳动，不改并行结构，**风险最低**；多个模型都做"按 X 分组聚合"时省最多。
- **代价 / 风险**：
  - 需要识别"公共步骤"。模型算的指标差异大 → 公共部分少 → 收益小。
  - 收益上限不如并行（并行是把 N 段变 1 段；预计算只是去掉重复段）。
  - 要设计好"哪些料该先备"、模型怎么从上游取，改的是引擎调度逻辑。
- **适合**：作为 A 的搭档一起上，进一步压低每个模型的耗时。

### C. 结果缓存（同样的分析不二算）

- **干啥**：同样的数据 + 同样的意图，第一次算完存起来（数据指纹 hash 当钥匙），下次直接返回。
- **收益**：完全消除重复计算。对"用户反复看同一分析""前端重复请求""调试反复重跑"特别有效；实现简单。
- **代价 / 风险**：
  - **只对"重复"场景有效，首次算还是慢**——治不了"第一次点就很慢"。
  - 要决定存哪（内存 / 磁盘）、多久失效、怎么判断"同样的数据"（大文件 hash 本身也耗时）。
  - 结果集占内存（100MB 结果 × N 个分析组合）；数据一变就要失效重算。
- **适合**：提升"反复看 / 重复请求"的体验，不能替代首次提速。

### D. 换计算引擎（polars / duckdb 替代 pandas）

- **干啥**：底层用 C++ 向量化库替代 pandas，很多操作 5~50 倍提速。
- **收益**：提速最狠，且常常"顺手"把 A/B/C 的收益一起放大。
- **代价 / 风险**：**改动最大**——所有模型的代码可能要重写 / 适配，回归测试多；风险最高，应是最后一步。
- **适合**：前面三招都上完还不够时再考虑。

## 二、四者关系（不是四选一）

```
        首次也快？   重复请求快？   改动量   风险
A 并行     ✅           ✅          中      中（GIL/进程开销）
B 预计算   ✅           ✅          中      低
C 缓存     ❌(首慢)     ✅          低      低
D 换引擎   ✅(最狠)     ✅          大      高
```

- A + B 是**治本组合**：B 压低单模型耗时、A 把串行变并行，一起上最稳。
- C 是**体验补丁**：专治"反复点 / 重复请求"，首次无感。
- D 是**终极大招**：前三者到位仍不够再动。
- 推荐落地顺序：**先量（加计时定位真瓶颈）→ A(+B) → C → 最后 D**。

## 三、关键前置：先量再改

不先量就优化，容易白忙。建议在 `run_analysis` 里给每个 `model.compute` 包一层耗时打印（模型名 + 秒数），跑一次真实数据，看：
1. 是不是真在 Phase 1 串行排队（总耗时 ≈ 各模型相加）；
2. 哪几个模型最慢（决定并行收益上限）；
3. 是否有公共因子计算被重复（决定 B 收益）。

量清楚再选方案，避免"感觉慢就并行、并行了发现是某个模型内部慢"的弯路。
