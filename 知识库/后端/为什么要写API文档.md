# 为什么要写 API 文档

## 本质：系统之间的"合同"

API 文档告诉所有调用方：**怎么调、传什么、返回什么、出错怎么办**。是前后端、系统之间的**契约**。

## 谁在看文档

| 读者 | 为什么需要 |
|---|---|
| 前端工程师 | 知道路径 / 参数 / 返回结构才能调用（项目里 `frontend/src/api` 是文档的代码落地版） |
| 后端 / 同事 | 改接口前确认影响面 |
| 测试 | 按文档设计用例 |
| 新人 / 接手者 | 不通读源码也能上手 |
| 第三方接入方 | 对接的唯一依据 |

## 不写文档的代价

- 联调靠口头约定 + 看源码 + 抓包 → 慢、易错
- 改了接口对方不知道 → 线上 bug
- 新人上手成本高

## 自动文档省"手写"，但"需要文档"不变

[[代码即文档|FastAPI 代码即文档]] 省去手写体力活，但只解决了"接口长什么样"，表达不了：

- **错误码约定**：400 / 422 / 500 各自含义（PRD 4.4.4 契约 I 系列）
- **降级策略**：LLM 无 Key / 失败降级为规则摘要
- **鉴权与限流**：上线时如何控制访问
- **业务边界**：缺失值自动填充还是删行

这些解释性内容必须人写，代码生成不出。

## 项目里文档的三处落点

1. `/docs` 自动页 —— 接口形状（FastAPI 生成）
2. `PRD_DataMind_AI.md` 4.4.4 接口与依赖说明 —— 接口规则（人写）
3. `frontend/src/api/*.ts` —— 文档的代码实现

## 一句话

**写 API 文档 = 把接口契约讲清，让调用方不读源码也能对接，避免联调返工和线上 bug。自动文档覆盖"形状"，错误码 / 降级 / 边界仍需人写。**
