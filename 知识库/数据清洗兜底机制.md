# 数据清洗兜底机制

> 对应代码：`backend/routers/clean.py`（L319-362）+ `backend/services/session_manager.py`（L328-349）。
> 这是 [[数据清洗AI规则_prompt约束]] 里"安全网"三道**代码级兜底**的详细展开版。
> 核心观点：**兜底=最后保险**。prompt 约束在前置防呆，确定性代码真正执行，备份回滚兜底——三层互补。

## 一、为什么要兜底

[[数据清洗AI规则_prompt约束]] 里的 5 条"注意"全是 prompt 约束，但 AI 仍可能违反（比如返回第 5 种未定义的 action）。所以后端在代码层再垫三道保险，确保**任何情况下数据都不会被搞坏、程序都不会卡死**。

## 二、三道兜底分别是什么

### ① Undo 点（L326）—— 给用户"反悔键"

```python
# clean.py L326（AI 清洗循环内，每步执行前）
manager.push_undo_state(req.session_id)
```

`push_undo_state` 是 **append（非破坏）**，把当前 `df` 的副本压入会话的 `df_undo_stack`（上限 20）：

```python
# session_manager.py L328-340（节选）
def push_undo_state(self, session_id):
    session = self._get(session_id)
    session.df_undo_stack.append(session.df.copy())   # ← 追加，不删旧
    if len(session.df_undo_stack) > 20:
        session.df_undo_stack.pop(0)
```

对应的"反悔"是 `undo_last_action`，它是 **pop（破坏）**——消耗掉栈顶历史：

```python
# session_manager.py（节选）
def undo_last_action(self, session_id):
    prev_df = session.df_undo_stack.pop()              # ← 弹出，历史减少
    session.df = prev_df.copy()
```

> 作用：用户觉得 AI 某一步洗坏了，可以一键退回 N 步前（每次修改都拍快照）。

### ② DataFrame 备份（L327）—— 单步原子恢复

```python
# clean.py L326-327
manager.push_undo_state(req.session_id)   # 撤销点
df_backup = df.copy()                     # ← 本轮"执行前快照"
```

`df_backup` 是**局部变量**，永远保存"本轮 `try` 开始前的 df"。一旦执行抛异常，原地还原：

```python
# clean.py L360-362（节选）
except Exception as e:
    df = df_backup                       # ← 单步原子恢复
    applied.append({"step": ..., "reason": f"执行失败: {str(e)}", "success": False})
```

> 作用：防止"洗到一半的脏数据"被返回给前端。每一步要么整步成功、要么整步回滚，不存在中间态。

### ③ 异常跳过（L360-362）—— 整体不崩

同上的 `except` 分支。遇到**未定义的 action**（第 5 种）或**执行报错**时：
1. `df` 还原到 `df_backup`（不污染数据）；
2. 该步 `success: False` 记入 `applied`（带失败原因）；
3. **循环继续**，跳到下一步。

> 作用：不跳过的话，一个坏步骤会让程序卡死、前端永远收不到返回。异常跳过保证"能洗的都洗了，洗不了的标记出来"，整条链路总能返回一个完整结果。

## 三、四个常见误解澄清（重点）

### Q1：② 出错时，不能用 ① 的快照继续清洗吗？

**不能互替。** ① `push_undo_state` 是 **append**（只是入栈，不动当前 df），② `df_backup` 是工作副本的本地镜像。真正"回退"靠的是 `undo_last_action` 的 **pop**——它会**消耗**栈顶历史、改动 `session.df` 本身，属于"用户手动反悔"语义。

如果单步失败也走 `undo_last_action` 来恢复，会带来三个问题：
- **步数计数污染**：一次失败 == 一次用户反悔，后续"撤销 N 步"的语义全乱；
- **栈顶错位**：`df_backup` 永远是最新一步前，而 undo 栈里可能还压着更早的版本，混用会弹出错误的版本；
- **加锁/拷贝开销**：undo 要操作会话级共享栈并加锁，单步恢复用局部变量 `df_backup` 零开销。

所以设计上**两份存储是物理必然**：undo 栈服务"用户反悔"（跨步、持久），`df_backup` 服务"单步原子"（本步、瞬态），职责不同。

### Q2：为什么不能只存一份快照、边算边更新？

理论上"只保留快照、随计算更新、异常时回找快照"确实省一份内存——但代价是：

- 你仍需一个**独立的工作副本**来承载当前这步的"脏状态"（还没算完的中间结果），本质还是两份；
- 边算边覆盖快照 = **丢掉撤销历史**，用户再也不能退回更早的版本。

所以"只存快照"省不掉真实成本，反而丢了 ① 的跨步撤销能力。

### Q3：异常时换成原始数据，是不是要重头重算？

**不会重头算。** `df_backup`（L327）拷贝的是"本轮 `try` 开始前"的 df，也就是"原始 + 已完成的 A、C 步"，**不是最初上传的原始数据**。异常发生时：
- 只丢弃**出错的这一步 B**；
- A、C 等已成功步骤的结果**保留在 `df_backup` 里**，不回退、不重算。

所以"回退"是"回退一圈（本轮）"，不是"回退到零（最初）"。

### Q4（用户原话）："将快照看成是源数据，抛异常时就找快照"

这正是代码的**等效心智模型**：你心里的"源" = 代码里的 `df_backup`。代码已经按这个模型实现了——

- `df_backup` = 你眼中的源快照；
- `except: df = df_backup` = 抛异常就找快照恢复；
- 唯一差异在**命名**（`df_backup` 强调"本轮前"，不叫 source）和**与撤销历史解耦**（undo 栈另存，可跨步反悔）。

用"快照当源"来理解完全正确，无需改代码。

## 四、三层分工与互补

| 兜底 | 触发方 | 恢复粒度 | 与谁绑定 |
|---|---|---|---|
| ① Undo 点 | 用户主动点"撤销" | 跨步（N 步前） | 独立（用户反悔） |
| ② DataFrame 备份 | 单步执行前自动拍 | 本轮（原子） | 与 ③ **绑定** |
| ③ 异常跳过 | 单步抛异常自动触发 | 本轮（原子） | 靠 ② 还原 |

- **②③ 强绑定**：③ 能恢复，是因为 ② 先拍了 `df_backup`；没有 ②，③ 只能 `continue` 却恢复不出干净数据。
- **① 独立**：服务于"用户不满意想反悔"，与自动回滚是两套语义。
- 整体效果：**prompt 约束（前置防呆）+ 确定性代码（真正执行）+ 备份回滚（兜底）** 三层保险。
