# 分析流水线现状（点击分析到装包）

> 对应代码（按调用顺序）：
> - 入口层：`backend/routers/analysis.py`（`/analysis/run`、`/analysis/process-datasets`）
> - 共享编排层：`backend/routers/_analysis_pipeline.py`（`run_intents_to_packages`）
> - 规则选择器：`src/planner.py`
> - 模板/计算层：`src/analysis_templates/*.py`、`src/analysis_templates/base.py`（AnalysisPackage）
> - 图表层：`src/chart_renderer.py` → `src/echart_generator.py`
> - 全局：`src/utils/json_serializer.py`（sanitize_json）
>
> 本笔记是 [[数据洞察分析后端全链路]] 的**第 3 步编排细化 + 统一数据源契约**补充：那里侧重「AI 对话两阶段（出意图→执行）」，这里讲清楚流水线内部对每个 intent 到底做了什么、产出的 Package 被谁消费。

## 〇、一句话总览

```
列名映射 → 纯规则 Planner 选模板 → 模板 execute 产出 AnalysisPackage
         → chart_renderer 渲染 ECharts → 同一 Package 同时喂「可视化大屏」与「AI 分析报告」
```

业务 5 步中的第 3 步「点击分析」= 上面整条；第 4、5 步都从 **AnalysisPackage** 取数，不各自私有结构。

## 一、两个入口

| 入口 | 触发 | 关键代码 | 意图来源 |
|---|---|---|---|
| `POST /analysis/run` | 用户点「分析」单数据集 | `analysis.py:52` | 前端传入的 `intents`（用户选的分析目标） |
| `POST /analysis/process-datasets` | 多数据集并行处理 | 实际执行 `_process_one`（`analysis.py:111`，线程池限 2 并发） | `Planner.generate_default_intents(df)` 纯规则生成（`analysis.py:119`） |

两者都先 `map_dataset_columns(...)` 做列名映射（统一为规范标准名，见 [[列名映射子系统]]），再交给共享流水线。

## 二、共享流水线 `run_intents_to_packages`

定义在 `backend/routers/_analysis_pipeline.py:130`，对每个分析意图跑一遍：

```
1. _PLANNER.plan(intent, df)          → plan
   (analysis_method / algorithm / dimension / metric / derived_df)
   └─ planner 内部（src/planner.py）：
      Library 查询 → 缺失列派生（确定性规则，见下）→ fallback 链 can_run
      → 列推断 / 词云专项重选 → 校验
2. method == "unsupported"
   → _try_fallback_chain（按 YAML fallback 顺序逐一 can_run）
     或 _unsupported（带 suggestion，按分析类型动态生成，非统一提示）
3. 否则 _execute_with_fallback(...)   (_analysis_pipeline.py:63)
   └─ _get_template_class(method) 动态加载模板类
      → template.can_run(df) 校验
      → template.execute(df, dim, met, algorithm) 返回 AnalysisPackage
      → 运行条件不符则按 YAML runtime.FALLBACK 递归降级（depth≤5）
4. result.charts = _RENDERER.render_all(result.chart_data)   (_analysis_pipeline.py:176)
   └─ 把 chart_data 渲染成 ECharts option（即 rendered_charts）
5. 装包：生成 pkg_id；dataclasses.asdict(result) 进 packages（sanitize 后返回前端）
         package_map[pkg_id]=result 存进 session（看板/报告统一读取入口）
```

### Planner 缺失列派生（确定性，非 LLM）

`src/planner.py:_derive_missing_columns`（记忆 16220326）：
1. 需数值指标且缺失、有维度列 → 自动生成 `__derived_count__` 计数指标；
2. 需日期维度且缺失、有 年/月(日) 列 → 合并生成 `__derived_date__`；
3. 需分类维度且缺失、有任意文本列 → 放宽选用该文本列（词云友好）。
派生成功则不判 `unsupported`。

## 三、统一数据源：AnalysisPackage

- **定义**：`src/analysis_templates/base.py:106`。核心字段：
  `analysis_type / findings / kpis / chart_data / charts / tables / insights / conclusions / suggestion` 等。
- **存储**：`session_manager.analysis_packages`，看板/报告统一读取入口（`analysis.py:69` set；dataset 切换时同步 `analysis.py:478`）。
- **后端只出 ECharts option、不出图**：详见 [[图表渲染架构_后端只出ECharts_option]]。

### 三个消费方

| 消费方 | 代码 | 说明 |
|---|---|---|
| 可视化大屏 | `card_generator.py` → `src/dashboard/*`（composition_planner / section_planner） | 从 package 的 kpis/tables/charts/insights 生成 `cards`（医疗模板唯一数据源） |
| AI 分析报告 | `report_builder.py` + `ai_agent/agent.py` 的 `generate_ai_report` | 读取 AnalysisPackage 组织语言；prompts.py V3 规定「所有数字必须来自 AnalysisPackage，不得编造」 |
| 推理引擎 | `reasoning/rule_engine.py` | 消费多个 AnalysisPackage 构建事实图 + 推断结论 |

### 前端消费侧（来自工程记忆）

- 大屏：`DashboardPage → EGridLayout → EChartView`，option 取自 `pkg.rendered_charts`。
- 报告：`generateAIReport` 五阶段流水线，Section 与 `chartIndex` 绑定 echarts，容器 420px，以实际数据为准。

## 四、与「LLM 分析决策层」计划的关系

本笔记描述的「纯规则 Planner 选模板」正是计划中**要插入 LLM 决策层的位置**：

- 插入点 = **列名映射之后、Planner 之前**；
- 比对基准 = 本笔记的写死分析模型（`analysis_library/*.yaml` + `analysis_templates/*.py`，含 retention 同期群）；
- 输出归一化 = LLM 方案与写死模型比对后的结果，最终仍统一写入 **AnalysisPackage**（第三节契约不变），前端大屏/报告取数方式无需变。

> LLM 生成代码并运行的模块写入计划但本次留桩，复用 `ai_agent/agent.py` 的 `_execute_code` 作为未来执行通道。
